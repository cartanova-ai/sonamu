# miomock Contract

> Last modified: 2026-04-14

## 개요

miomock은 중소규모 기업을 위한 사내 통합 관리 플랫폼이다. 조직 관리, 프로젝트 관리, 문서 관리를 하나의 시스템에서 제공하여 현재 조직도/프로젝트/문서가 서로 다른 도구에 분산되어 있는 문제를 해결한다.

하위 도메인:

- **auth** — 사용자 및 인증
- **organization** — 회사, 부서, 직원
- **project** — 프로젝트, 태그, 마일스톤, AI 어시스턴트
- **document** — 문서 작성 및 의미 검색
- **file** — 파일 업로드 및 관리
- **audit** — 감사 로그
- **dashboard** — 현황 집계 대시보드

## 도메인 용어

### 사용자/조직

- **사용자**: 시스템에 가입한 개인. 이메일로 식별한다.
- **세션**: 로그인 성공 시 생성되는 인증 유지 단위. 1년간 유효하다.
- **외부 계정**: Google, GitHub 등 OAuth 제공자를 통해 연결된 계정.
- **패스키**: 지문, 얼굴 인식 등 생체 정보 또는 보안 키를 이용한 비밀번호 없는 로그인 수단.
- **2단계 인증(2FA)**: OTP 앱을 통해 로그인 시 추가 코드를 입력하는 보안 강화 수단.
- **백업 코드**: 2FA를 활성화할 때 발급되는 비상용 일회성 코드.
- **이메일 검증**: 가입 후 이메일 소유권을 확인하는 절차.
- **역할**: 사용자에게 부여되는 권한 등급 (일반 사용자, 관리자).
- **회사**: 관리 대상이 되는 기업 단위. 멀티 테넌트가 아닌, 관리 목록으로서의 회사.
- **부서**: 회사 내 조직 단위. 상하 관계를 가질 수 있다 (예: 개발본부 > 백엔드팀 > 서버파트).
- **부서 코드**: 부서 생성 시 자동 부여되는 고유 식별 번호 (`DEP-001`, `DEP-002`, ...).
- **직원**: 사용자 중 조직에 등록된 사람. 사번으로 식별한다.
- **사번**: 직원에게 부여되는 고유 번호.
- **미배치**: 어느 부서에도 속하지 않은 직원 상태.

### 프로젝트/문서/파일

- **프로젝트**: 이름, 설명, 예산, 마감일을 가진 업무 단위.
- **프로젝트 상태**: `planning`(기획 중) / `in_progress`(진행 중) / `completed`(완료) / `cancelled`(취소).
- **태그**: 프로젝트를 분류하기 위한 키워드. 다국어(한국어, 영어, 일본어)를 지원한다.
- **전문 검색**: 프로젝트 이름과 설명을 대상으로 한 텍스트 기반 검색.
- **AI 어시스턴트**: 프로젝트 관련 질문에 실시간으로 답변하는 대화형 도우미.
- **마일스톤**: 프로젝트의 주요 체크포인트. 이름, 목표일, 완료 여부를 가진다.
- **타임라인**: 프로젝트의 마일스톤들을 시간순으로 나열한 것.
- **문서**: 제목과 본문으로 구성된 사내 문서.
- **문서 상태**: `draft`(초안) / `published`(게시) / `archived`(보관).
- **의미 검색**: 키워드 일치가 아닌, 내용의 의미가 유사한 항목을 찾아주는 검색 방식.
- **파일**: 업로드된 파일. 이름, URL, MIME 타입으로 구성된다.
- **중복 감지**: 같은 파일을 다시 업로드할 때 이를 인식하는 기능.

### 감사/대시보드

- **감사 로그**: 일반 엔티티 변경 시 자동 생성되는 이력 레코드 (`audit_logs`).
- **감사 이벤트**: Better Auth가 발행하는 인증/조직 관련 이벤트 로그 (`audit_events`).
- **액터**: 변경을 수행한 사용자.
- **대상 엔티티**: 변경이 발생한 테이블/레코드.
- **액션**: `create` / `update` / `delete`.
- **변경 내역**: 변경 전/후 값의 차이 (JSON diff).
- **dedupe_key**: 동일 이벤트의 중복 적재를 방지하기 위한 해시 키.
- **카테고리**: 감사 이벤트의 상위 범주 (`user`, `session`, `account`, `organization`, `security`).
- **메트릭 카드**: 단일 숫자와 레이블로 구성된 요약 정보 단위.
- **조직/프로젝트/문서 현황**: 각 도메인 엔티티 카운트와 상태별 집계를 요약한 메트릭 카드 그룹.
- **활동 타임라인**: 감사 로그 기반으로 날짜별 그룹핑한 최근 변경 이력 목록.
- **기간 필터**: 활동 타임라인의 조회 범위 (7일/30일/전체).

### 공용

- **soft delete**: 데이터를 즉시 파기하지 않고 비활성 상태로 보관하는 삭제 방식.
- **hard delete**: 데이터를 즉시 영구 삭제하는 방식.

## 사용자 역할

- **일반 사용자**: 자기 프로필 관리, 프로젝트 확인, 문서 작성 및 검색, 파일 업로드. 데이터 조회/생성/수정 가능.
- **관리자 (HR/운영팀)**: 일반 사용자 권한 + 삭제 권한. 회사/부서/직원/프로젝트 전반 관리, 태그/마일스톤 관리, 파일 삭제, 전체 감사 로그 조회, 사용자 계정 삭제, 보안 정책 관리.
- **시스템 관리자**: 사용자 계정 및 시스템 보안 정책 관리.

일반 사용자는 활동 타임라인에서 본인의 변경 이력만 조회할 수 있다. 관리자는 전체 이력을 조회한다.

## 공통 규칙

- 모든 삭제는 관리자만 수행할 수 있다.
- 목록 조회의 기본 페이지 크기는 24건이다. 페이지 크기를 0으로 지정하면 전체 조회가 가능하다.
- 목록 응답에는 전체 건수, 현재 페이지, 전체 페이지 수를 포함한다.
- 시스템 기본 언어는 한국어이며, 영어와 일본어를 추가 지원한다. 현재 다국어 적용 대상은 태그 이름이다.

### 고유성 제약

- 사용자 이메일: 시스템 전체에서 유일.
- 회사 이름: 시스템 전체에서 유일.
- 부서 이름: 같은 회사 안에서 유일.
- 사번: 시스템 전체에서 유일.
- 파일 URL: 시스템 전체에서 유일.

### 삭제 정책

- 사용자 삭제는 soft delete (데이터 보존, 이메일 점유 유지).
- 회사/부서 삭제는 hard delete + 연쇄 삭제.
- 부서 삭제 시 소속 직원은 삭제하지 않고 미배치 처리.
- 사용자 삭제 시 연관된 인증 데이터(세션, 패스키, 2FA, 외부 계정)와 직원 레코드는 연쇄 삭제.
- 프로젝트 삭제 시 소속 마일스톤은 CASCADE로 함께 삭제.

## 데이터 관계 요약

```
회사 ─┬── 부서 (계층)
      │    └── 직원 ←→ 사용자 (1:1)
      │        └── 프로젝트 참여 (다대다)
      │            ├── 태그 분류 (다대다)
      │            ├── 마일스톤 (1:N)
      │            └── 이미지 첨부
문서 (독립)
파일 (독립)
감사 로그/이벤트 (독립)
```

- 프로젝트와 직원/태그는 다대다 관계이며, 저장 시 제거된 항목은 즉시 배정 해제된다.
- 부서 상위 관계는 자기 참조 nullable로 계층 구조를 형성한다.

## 공통 엣지케이스

- 삭제된 사용자의 이메일로 재가입을 시도하면 거부한다.
- 2FA 백업 코드를 모두 소진한 사용자는 스스로 복구할 수 없으며, 관리자 개입이 필요하다.
- 회사 삭제 시 소속 부서는 연쇄 삭제되지만, 소속 직원은 미배치 상태로 전환된다.
- 같은 파일을 중복 업로드하면 시스템이 이를 감지한다.

## auth — 사용자 및 인증

### 개요

사용자 인증 및 계정 관리 도메인이다. 이메일 기반 가입/로그인을 기본으로 하며, 외부 계정 연동, 패스키, 2단계 인증 등 다양한 보안 수단을 제공한다.

### 규칙

- 사용자 이메일은 시스템 전체에서 유일해야 한다.
- 한 사용자는 하나의 역할(일반 사용자 또는 관리자)을 가진다.
- 세션 유효 기간은 1년이다.
- 이메일 검증 토큰에는 만료 기간이 있다.
- 사용자 삭제 시 연관된 인증 데이터(세션, 패스키, 2FA, 외부 계정)를 연쇄 삭제한다.

### 엣지케이스

- 삭제된 계정의 이메일로 재가입을 시도하면 거부한다 (soft delete 상태에서도 이메일 점유 유지).
- 2FA 백업 코드를 모두 소진하면 사용자 스스로 복구할 수 없다. 관리자가 2FA를 해제해야 한다.
- 이메일 검증 링크가 만료된 경우 새로운 검증 메일을 재발송해야 한다.
- 외부 계정만으로 가입한 사용자가 해당 외부 계정을 해제하면 로그인 수단이 없어질 수 있다.

### 기능

- **회원가입 (signup)** — 이메일, 비밀번호, 이름으로 사용자를 생성한다. 중복 이메일은 유니크 제약 위반으로 거부된다.
- **로그인 (signin)** — 이메일/비밀번호로 로그인 시 세션(유효 1년)을 생성하고, 로그인 시점의 IP와 접속 환경을 세션에 기록한다.
- **이메일 검증 (email-verification)** — 가입 후 만료 기간이 있는 검증 토큰을 발급한다. 검증 완료 시 정식 사용자로 전환된다. 만료 시 재발송이 필요하다.
- **소셜 로그인 (social-login)** — Google, GitHub 등 외부 계정으로 로그인한다. 한 사용자는 여러 외부 계정을 연결할 수 있다. 사용자 삭제 시 외부 계정 연결은 함께 삭제된다.
- **패스키 (passkey)** — WebAuthn/FIDO2 기반 패스키를 등록해 비밀번호 없이 로그인한다. 기기 유형(플랫폼/크로스플랫폼)과 백업 여부를 기록한다. 사용자 삭제 시 패스키는 함께 삭제된다.
- **2단계 인증 (two-factor)** — TOTP(OTP 앱) 기반으로 활성화/비활성화한다. 활성화 시 비상용 백업 코드를 발급한다. 로그인은 비밀번호 인증 후 OTP 추가 입력이 필요하다. 사용자 삭제 시 함께 삭제된다.
- **사용자 프로필 (user-profile)** — 이름, 생년월일, 자기소개, 프로필 이미지를 본인이 수정한다. 단건/목록 조회는 서브셋에 따라 반환 필드를 제어하며, 목록은 페이지네이션과 검색을 지원한다.
- **비밀번호 재설정 (password-reset)** — 이메일로 재설정 링크를 발송한다. 재설정 토큰 유효 기간은 1시간이다. 미등록 이메일 요청에도 동일 성공 응답을 반환한다(타이밍 공격 방지). 재설정 완료 시 해당 사용자의 기존 세션은 전부 무효화된다.
- **계정 삭제 (account-deletion)** — 관리자만 삭제할 수 있으며, `deleted_at` 기반 soft delete로 비활성화한다. 외부 계정, 패스키, 2FA는 CASCADE로 함께 삭제된다.

## organization — 회사, 부서, 직원

### 개요

조직 관리 도메인이다. 회사 아래에 부서가 계층 구조로 존재하고, 직원은 부서에 배치되거나 미배치 상태로 관리된다.

### 규칙

- 회사 이름은 시스템 전체에서 유일해야 한다.
- 같은 회사 안에서 부서 이름은 유일해야 한다.
- 한 사용자는 하나의 직원 레코드만 가질 수 있다 (중복 등록 불가).
- 사번은 시스템 전체에서 유일해야 한다.
- 회사 삭제는 소속 부서를 연쇄 삭제한다 (hard delete).
- 부서 삭제는 하위 부서를 연쇄 삭제한다.

### 엣지케이스

- 부서 삭제 시 소속 직원은 삭제하지 않고 미배치 상태로 전환한다.
- 이미 직원으로 등록된 사용자를 다시 직원으로 등록하려 하면 거부한다.
- 존재하지 않는 회사에 부서를 생성하려 하면 거부한다.
- 부서의 상위 부서를 자기 자신이나 자신의 하위 부서로 지정하면 순환 참조가 발생할 수 있다.
- 직원이 배치된 부서가 삭제되면 해당 직원은 자동으로 미배치 상태가 된다.

### 기능

- **회사 (company)** — 회사를 생성/수정/삭제한다. 이름은 시스템 전체에서 유일하며, 목록 조회는 이름 LIKE 검색을 지원한다. 관리자만 삭제할 수 있고 삭제 시 소속 부서는 CASCADE로 함께 삭제된다.
- **부서 (department)** — 회사 ID와 선택적 상위 부서 ID로 생성/수정한다. 부서 코드는 `DEP-001` 형식으로 자동 부여된다. 목록 조회는 이름 검색과 회사명 필터를 지원하며, 응답에 소속 직원 수가 포함된다. 같은 회사 내 중복 이름은 유니크 제약 위반으로 거부된다. 관리자만 삭제할 수 있으며, 삭제 시 소속 직원의 부서 배치는 NULL로 전환된다.
- **직원 (employee)** — 가입된 사용자와 1:1로 연결해 등록하고 사번을 부여한다. 부서 배치는 선택이며 급여/입사일을 기록한다. 프로젝트와 다대다 관계를 가진다. 목록 조회는 사번 LIKE 검색을 지원하고, ID 검색은 숫자만 허용한다(비숫자는 빈 결과). 관리자만 삭제할 수 있다.

## project — 프로젝트, 태그, 마일스톤, AI 어시스턴트

### 개요

프로젝트를 생성하고 상태를 관리하며, 직원을 배정하고, 태그로 분류한다. 전문 검색과 AI 어시스턴트 기능을 포함하고, 마일스톤으로 프로젝트 일정을 관리한다.

### 규칙

- 프로젝트와 직원은 다대다 관계이다 (한 직원이 여러 프로젝트에, 한 프로젝트에 여러 직원).
- 프로젝트와 태그는 다대다 관계이다.
- 프로젝트 저장 시 배정/태그 목록이 변경되면, 제거된 항목은 즉시 배정 해제된다.
- 태그 목록은 자주 조회되므로 빠른 응답을 위해 캐시를 사용한다.
- 마일스톤은 프로젝트에 종속된다 (프로젝트 삭제 시 마일스톤도 삭제).
- 마일스톤 목표일은 프로젝트 마감일 이후일 수 없다 (마감일이 설정된 경우).
- 완료된 마일스톤은 수정 가능하며, 완료 상태를 되돌릴 수도 있다.
- 프로젝트가 `completed`/`cancelled` 상태일 때는 마일스톤을 새로 추가할 수 없다.

### 엣지케이스

- 프로젝트에 배정된 직원이 퇴사(삭제)된 경우의 처리.
- 프로젝트에 사용 중인 태그를 삭제하려는 경우의 처리.
- 마감일이 이미 지난 프로젝트의 상태를 `planning`이나 `in_progress`로 변경하는 경우.
- 전문 검색 시 한국어/영어 혼용 검색어 처리.
- 프로젝트 마감일이 변경되어 기존 마일스톤 목표일보다 앞당겨진 경우.
- 프로젝트가 `completed`/`cancelled` 상태일 때 마일스톤 추가를 시도하면 거부한다.

### 기능

- **프로젝트 관리 (project-management)** — 이름, 설명, 예산, 마감일, 상태, 이미지(여러 장)로 생성/수정/삭제한다. 관리자만 삭제할 수 있다.
- **인력 배정 (project-staffing)** — 저장 시 직원/태그 ID 목록으로 배정을 동기화한다. 저장 시 제외된 항목은 즉시 배정 해제된다. 동기화는 저장 트랜잭션 내에서 일관되게 처리된다.
- **태그 (tag)** — 태그를 생성/수정/삭제한다. 기본 이름과 다국어 이름(`name_ko`, `name_en`)을 저장한다. 조회는 캐시를 사용하며 히트 시 즉시 반환, 미스 시 DB 조회 후 캐시에 저장한다. 캐시는 명시적으로 무효화할 수 있다. 태그 관련 배경 워크플로우(`scrape-data` → `process-data` → `save-data`)를 실행할 수 있다. 관리자만 삭제할 수 있다.
- **프로젝트 검색 (project-search)** — 이름/설명 기반 전문 검색을 지원한다. 이름 가중치 3, 설명 가중치 1로 점수를 계산하고 점수 순으로 결과를 반환한다.
- **AI 어시스턴트 (project-ai-assistant)** — 사용자 질문에 대해 실시간 스트리밍으로 답변한다. 에이전트는 프로젝트 데이터 조회 도구를 통해 관련 데이터를 참조한다.
- **마일스톤 (milestone)** — 프로젝트에 속한 마일스톤을 생성/수정/삭제한다. 목표일이 프로젝트 마감일 이후이거나, 프로젝트가 `completed`/`cancelled` 상태일 때 추가를 시도하면 거부한다. 완료 처리 및 완료 취소가 가능하다. 목록은 `project_id` 필터와 페이지네이션을 지원하며 기본 정렬은 목표일 오름차순이다. 프로젝트 삭제 시 CASCADE로 함께 삭제된다.

## document — 문서 작성 및 의미 검색

### 개요

사내 문서를 작성하고 상태를 관리하며, 의미 검색을 통해 관련 문서를 찾을 수 있다.

### 규칙

- 문서는 독립 엔티티로, 다른 도메인(회사, 프로젝트 등)과 직접적인 관계를 갖지 않는다.
- 문서 생성 시 기본 상태는 `draft`이다.
- 상태 값은 `draft | published | archived`만 허용한다.

### 엣지케이스

- 보관 상태의 문서를 다시 게시 상태로 되돌리는 경우.
- 의미 검색 시 검색어와 유사한 문서가 전혀 없는 경우의 응답 처리.
- 매우 짧은 본문(한두 단어)의 문서에 대한 의미 검색 품질.

### 기능

- **문서 작성 (document-creation)** — 제목과 본문으로 생성/수정/삭제한다. 생성 시 기본 상태는 `draft`이다. 관리자만 삭제할 수 있다.
- **문서 상태 (document-status)** — 상태는 `draft` → `published` → `archived` 흐름을 따른다. 상태 정보는 문서 레코드와 함께 원자적으로 저장된다.
- **의미 검색 (semantic-search)** — 검색어를 임베딩 벡터로 변환해 벡터 유사도 기반 검색을 수행한다. 유사 문서를 점수와 함께 반환한다. 일반 목록 조회에서도 의미 검색 쿼리가 주어지면 의미 검색 경로를 사용한다. 유사도 계산은 코사인 거리 기반이며 임계값 설정을 지원한다.
- **관리자 화면 (document-admin-ui)** — 관리자 화면에서 전체 문서를 테이블로 조회한다. 상태별 필터, 키워드 검색, 페이지네이션을 지원한다. 생성/수정 폼에서 제목(필수), 본문, 상태를 입력하며, 삭제 시 확인 다이얼로그를 거친다. 저장 성공 시 목록으로 이동하고 갱신된다.

## file — 파일 업로드 및 관리

### 개요

시스템에 파일을 업로드하고 관리한다.

### 규칙

- 파일 URL은 시스템 전체에서 유일해야 한다.
- 한 번에 업로드 가능한 파일 수는 최대 10개이다.
- 파일 크기 제한은 30MB이다.
- 파일은 독립 엔티티로, 다른 도메인과 직접적인 관계를 갖지 않는다.

### 엣지케이스

- 10개를 초과하는 파일을 한 번에 업로드하려는 경우 거부한다.
- 30MB를 초과하는 파일을 업로드하려는 경우 거부한다.
- 이미 존재하는 파일과 동일한 바이트의 파일을 업로드하는 경우 중복을 감지한다.

### 기능

- **파일 업로드 (file-upload)** — 멀티파트 요청으로 파일을 업로드한다(최대 10개, 30MB). 카테고리 지정 업로드는 최대 5개, 단일 파일 업로드는 최대 1개를 지원한다. 버퍼와 스트림 두 업로드 모드를 지원한다. 업로드 응답은 파일 URL, MIME 타입, 이름을 포함한다.
- **중복 감지 (file-deduplication)** — 업로드 시 MD5 해시 기반으로 중복 파일을 감지한다. 동일 해시/키의 파일이 이미 존재하면 기존 파일을 재사용한다. 기본 업로드 키는 `{md5}.{확장자}`, 카테고리 업로드 키는 `{category}/{md5}` 형식이다.
- **파일 관리 (file-management)** — 파일 메타데이터를 조회/수정/삭제한다. 관리자만 삭제할 수 있다. URL 유니크 제약을 유지한다.

## audit — 감사 로그

### 개요

시스템 내 주요 데이터 변경과 Better Auth 이벤트를 자동으로 기록하여 "누가, 언제, 무엇을, 어떻게" 변경했는지 추적한다. 두 축으로 관리된다. (1) 일반 엔티티의 생성/수정/삭제 기록(`audit_logs`), (2) Better Auth에서 발생하는 인증/조직 이벤트(`audit_events`).

### 규칙

- 감사 로그는 immutable이다 (삭제/수정 불가).
- 감사 로그 자체의 변경은 기록하지 않는다 (무한 재귀 방지).
- 인증 관련 이벤트(로그인, 로그아웃 등)는 일반 감사 로그(`audit_logs`)가 아닌 감사 이벤트(`audit_events`)로 별도 관리한다.
- 감사 로그 기록 실패는 원래 작업을 중단시키지 않는다 (로그 실패 ≠ 비즈니스 실패).
- 액터 ID는 현재 요청 컨텍스트의 사용자이며, 컨텍스트가 없는 시스템 작업은 null을 허용한다.

### 엣지케이스

- 배치 작업(여러 건 동시 수정) 시 각 건별로 개별 기록한다.
- 삭제된 사용자가 액터인 로그는 액터 정보를 그대로 보존한다 (orphan 허용).
- 동일 `dedupe_key`의 감사 이벤트 중복 수신 시, 두 번째부터는 예외 없이 silent 무시한다.
- 등록되지 않은 `event_type`의 감사 이벤트는 `user` 카테고리로 fallback 분류한다.

### 기능

- **감사 로그 자동 기록 (audit-log-recording)** — 대상 엔티티의 `save()`/`del()` 후 감사 로그가 자동 기록된다. 삭제 시에는 삭제 전의 값(`old_value`)을 조회해 기록한다. `old_value`/`new_value`는 JSON으로 저장되며 변경된 필드만 포함한다. 로그 기록 실패 시 원래 작업은 성공으로 처리된다. 감사 로그 테이블은 immutable이다.
- **감사 로그 목록 조회 (audit-log-query)** — 대상 엔티티, 액터, 기간 필터로 조회할 수 있다. 기본 정렬은 생성 시각 내림차순이며 페이지네이션을 지원한다.
- **감사 로그 상세 조회 (audit-log-detail)** — 단건 조회 시 `old_value`/`new_value` JSON을 포함해 반환한다. 존재하지 않는 ID를 조회하면 거부한다.
- **감사 이벤트 적재 (audit-event-ingestion)** — Better Auth가 발행한 이벤트를 `audit_events` 테이블에 1건씩 적재한다. 이벤트 원본(`eventData`)은 `payload_json`에 그대로 보존되며, 주요 필드는 promoted 컬럼으로 매핑된다. 발생 시각(`occurred_at`)과 적재 시각(`ingested_at`)은 별도로 기록한다. `event_type`에 따라 카테고리(`user`, `session`, `account`, `organization`, `security`)를 결정하며, 미등록 타입은 `user`로 fallback한다. 식별자는 `identifier → userEmail → memberEmail → inviteeEmail → acceptedByEmail → rejectedByEmail` 순의 폴백 체인을 따른다. `dedupe_key`는 지정 필드 조합의 sha256 해시로 계산하며, null 필드는 빈 문자열로 정규화 후 해시한다. 동일 `dedupe_key`로 중복 수신된 이벤트는 silent 무시한다.

## dashboard — 현황 집계 대시보드

### 개요

경영진이 조직, 프로젝트, 문서 현황을 한눈에 파악하고 최근 변경 활동을 확인할 수 있는 대시보드 도메인이다. 별도 엔티티나 테이블 없이 기존 도메인(organization, project, document, audit)의 데이터를 집계하여 제공한다.

### 규칙

- 별도 엔티티나 테이블을 생성하지 않는다. 기존 엔티티의 데이터를 집계한다.
- 전용 API 엔드포인트를 통해 모든 메트릭을 한 번의 요청으로 제공한다.
- 카운트 메트릭에는 필터를 적용하지 않는다 (항상 전체 데이터 기준).
- 기간 필터는 활동 타임라인에만 적용한다.
- 데이터는 페이지 진입 시 조회하며, 실시간 갱신은 하지 않는다.

### 엣지케이스

- 회사/부서/직원/프로젝트/문서가 0건인 경우: "아직 등록된 \[엔티티\]이 없습니다" 메시지를 표시한다.
- 진행중 프로젝트가 5개 미만이면 있는 만큼만 표시한다.
- 진행중 프로젝트가 0건이면 "진행중인 프로젝트가 없습니다" 메시지를 표시한다.
- 감사 로그가 0건이면 "최근 활동이 없습니다" 메시지를 표시한다.
- 선택 기간 내 감사 로그가 없으면 "해당 기간에 활동이 없습니다" 메시지를 표시한다.
- 마감일이 없는 프로젝트는 테이블에서 마감일 컬럼을 `-`으로 표시한다.
- 마일스톤이 없는 프로젝트는 진행률을 `0/0`으로 표시한다.

### 기능

- **현황 메트릭 집계 (dashboard-stats)** — 단일 API 호출로 조직/프로젝트/문서 메트릭을 모두 반환한다.
    - **조직 현황**: 회사 수, 부서 수, 직원 수.
    - **프로젝트 현황**: 상태별(`planning`/`in_progress`/`completed`/`cancelled`) 카운트와 진행중 프로젝트 상위 5건(마감일 임박순, null은 마지막). 각 상위 프로젝트는 마일스톤 진행률(완료/전체)을 포함한다.
    - **문서 현황**: 전체 문서 수, 상태별(`draft`/`published`/`archived`) 카운트, 최근 7일 내 생성된 문서 수.
    - 내부적으로 기존 도메인 모델의 조회 메서드를 재사용한다. 특정 섹션의 집계 실패 시 해당 섹션만 null로 반환하고 나머지는 정상 반환한다.
- **활동 타임라인 (activity-timeline)** — 감사 로그를 날짜별로 그룹핑하여 최근 20건을 반환한다. 각 항목은 액터명, 대상 엔티티/레코드 식별자, 액션(`create`/`update`/`delete`), 생성 시각을 포함한다. 기간 필터는 7일 / 30일 / 전체를 지원하며 기본값은 7일이다. 일반 사용자는 본인 이력만, 관리자는 전체 이력을 조회한다. 결과는 생성 시각 내림차순으로 정렬된다. "더보기"는 전체 감사 로그 페이지로 연결된다.
