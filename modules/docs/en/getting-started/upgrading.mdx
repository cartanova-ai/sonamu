## 0.13.12

### Auth secret is required

With auth enabled, the server no longer starts outside test (development, staging, and production) when the secret is missing or a publicly known value. Generate a value per environment with `openssl rand -base64 32` and set it in `BETTER_AUTH_SECRET` (or `server.auth.secret`). If you ran with a public value such as the former example fallback (`"miomock-secret-key-change-this-in-production"`), rotate the secret and revoke existing sessions. If you rotate keys with `secrets` or `BETTER_AUTH_SECRETS`, remove any public legacy key as well. CLI tasks that only call `init()`, such as `sync` and `migrate`, are not checked.

### Email verification no longer signs in 2FA users

For users with 2FA enabled, sessions newly issued by `/api/auth/verify-email` (including `autoSignInAfterVerification`) are now removed immediately. The verification or email change still takes effect. If a screen assumes the user is signed in right after verification, send the user to the normal sign-in flow instead.

### `user.additionalFields` now default to `input: false`

`user.additionalFields` entries without `input` are no longer accepted from sign-up (`/api/auth/sign-up/email`) or update (`/api/auth/update-user`) request bodies. If a request includes such a field, sign-up ignores it when the field has a `defaultValue`; otherwise the request fails with 400 `FIELD_NOT_ALLOWED`. Set `input: true` only on fields the client must provide, and never on permission fields such as `role`. See [Authentication setup](/en/api-development/authentication/setup) for details.

### Model scaffolding refused for credential Entities

The CLI and Sonamu UI now refuse to scaffold a Model for the Entities where better-auth stores credentials (`Session`, `Account`, `Verification`, `TwoFactor`, `Passkey`, `Jwks`, `ApiKey`, `SsoProvider`). Upgrading does not touch Models or entity.json subsets you already generated, so clean them up yourself.

- Remove the Model APIs scaffolded for these Entities, or add an admin guard to only the methods you need.
- Remove secret fields from their subsets (`Session.token`; `access_token`, `refresh_token`, `id_token`, and `password` on `Account`; `Verification.value`; `secret` and `backup_codes` on `TwoFactor`; `Jwks.private_key`; `ApiKey.key`; `oidc_config` and `saml_config` on `SsoProvider`), then run `sonamu sync`.

### Auth baseURL is required in remote environments

With auth enabled in staging or production, the server starts only when `server.auth.baseURL`, a better-auth environment variable such as `BETTER_AUTH_URL`, or an absolute http(s) `server.baseUrl` is set. This keeps password reset and email verification links from being built from the request `Host` header. A config that falls back to a local address, such as `` baseURL: process.env.BETTER_AUTH_URL ?? `http://${host}:${port}` ``, passes this check but produces wrong links in deployment, so always set `BETTER_AUTH_URL` when deploying.

### Environment selection when `NODE_ENV` is missing

When the runtime `NODE_ENV` is not set, Sonamu now checks `NODE_ENV` in `.env.local`, then `.env`, and uses a default only if neither has one. For `sonamu build`, `sonamu start`, and servers started with `createServer()`, that default changed from `development` to `production`. `sonamu dev`, tests, and CLI tools still default to `development`.

- Set `NODE_ENV` explicitly for development or staging servers you started without it. Otherwise they use the production settings and DB preset, and fail to start when neither `.env` nor `.env.production` exists.
- If `.env` or `.env.local` sets `NODE_ENV`, CLI tools such as `sync` and `migrate` use that environment too. For example, with `NODE_ENV=production` in `.env`, `migrate run` targets the production database.

### Startup warning for unguarded state-changing APIs, and `guardKeys`

The server now prints a startup warning for APIs without `guards` whose method is not GET, HEAD, or OPTIONS. Mark intentionally public APIs with `guards: []` and add suitable guards to the rest. If you list the keys your `guardHandler` actually checks in the new `server.apiConfig.guardKeys` option, any other key is rejected with 401 without calling `guardHandler`, and the server does not start while an API uses such a key. Without the option, every key is passed to `guardHandler` as before, so keys the handler does not check are allowed. See [Server configuration](/en/configuration/sonamu-config/server) for details.

### Async guards are awaited and `false` rejects

Sonamu now waits for the Promise returned by `guardHandler` before running the next guard or the API, and a `false` return rejects the request with `UnauthorizedException` (401). Previously, async guard rejections and `false` returns were ignored and the request ran anyway, so check any guard that relied on that: it now blocks requests. If you implement `lifecycle.onError` yourself, keep the status code of Sonamu exceptions, as in `isSoException(error) ? error.statusCode : 500`. Sending everything as 500 turns guard rejections into 500 too.

### Default-deny `guardHandler` in new projects

New projects created with `create-sonamu` ship a `guardHandler` that denies by default: `user` returns 401 when signed out, `admin` returns 403 when signed out or not an admin, and `query` or custom keys without checks return 403. Existing project configs are not changed, so if your `guardHandler` only logs, like the old template, or lets unhandled keys through, rewrite it the same way. Use a `ForbiddenException` defined in your project for 403. See [Authentication setup](/en/api-development/authentication/setup) for details.

### `BaseSaveParams` and the admin guard on scaffolded `save`

`sonamu.generated.ts` now exports `{Entity}BaseSaveParams` for each entity, a save-input schema without `created_at`, generated and searchText columns, and `readonly: true` props (the FK for relations), regenerated on every sync. Newly scaffolded `SaveParams` builds on it, and the scaffolded `save` API gets `guards: ["admin"]`. Existing `*.types.ts` files and models are not changed, so migrate them yourself.

- Set `readonly: true` on permission, verification-state, and secret props. It is not added to existing better-auth entity.json files either.
- Change `SaveParams` to `{Entity}BaseSaveParams.partial({ id: true })` and run `sonamu sync`. Where save inputs or forms used `created_at`, use the value from the fetched row instead.
- Review the `guards` on scaffolded `save` and other write APIs.

### `sonamuFilter` accepts only `toFilter` props

`sonamuFilter` now filters only props marked `"toFilter": true` in entity.json. To filter a relation FK (`{relation_name}_id`), mark the relation prop. Fields that are not allowed, and invalid operators or values, are rejected with `BadRequestException` (400) before the query runs, including when server code calls `findMany`. Mark only the fields you filter on with `toFilter: true` and run `sonamu sync`. Never mark secret fields such as passwords or tokens. See [sonamuFilter](/en/api-reference/base-model/sonamu-filter) for details.

### Guards and input validation for SSR preloads

SSR preloads now go through the API's `guards` and HTTP input validation. A guard rejection skips that preload, so the data is not prefilled in the HTML for visitors who do not pass the guard. If a preload that passed its guards has arguments that fail validation (for example `NaN` from `parseInt`), the whole page responds with 400, so review preloads that convert URL parameters. See [Data preloading](/en/frontend-integration/ssr/preloading-data) for details.

### Named types inside inline object parameters are validated

Named types inside an inline object parameter, such as `params: { data: UserSaveParams }`, used to pass without validation. They are now validated with the same Zod schemas as top-level parameters: invalid values are rejected with 400 and keys missing from the schema are stripped. Review clients that send values outside the schema in such parameters, and model code that relied on those values.

### Parameters with `null`, `undefined`, or boolean literals are validated

`null`, `undefined`, `void`, `true`, and `false` in API parameter types used to accept any value, and a union containing one of them (for example `"asc" | "desc" | null`) was not validated at all. Each now accepts only matching values, and anything else is rejected with 400. If a GET parameter is declared as a `true | false` union, its query string is not converted to a boolean and is rejected, so declare it as `boolean`. In GET, a union containing `number` converts the query string to a number before validation, so non-numeric strings are rejected.

### `tools/openVscode` restricts `absPath`

The Sonamu UI API `tools/openVscode` now opens an `absPath` only if it is an existing file under the app root (the parent directory of the API directory). Paths outside the app root, symlinks pointing outside it, directories, and missing files are rejected with 400. The file-open buttons in the UI keep working; only scripts that used this API to open files elsewhere need changes.

## 0.13.10

### Nested select nullability is decided by `id` only

Standalone Puri queries no longer append hidden presence columns (`"alias".* IS DISTINCT FROM NULL`) to the SQL. A nested group is now `null` only when its `id` is `null`. This replaces the presence description in the 0.13.3 section.

- A group whose name matches a LEFT JOIN alias, or whose fields read a LEFT JOIN alias, must select `id`; otherwise the query throws when executed. Add that alias's `id` to the group, or select the fields as flat aliases (`{ detail__note: "detail.note" }`). `rawQuery()` and `toQuery()` are not checked.
- A group mixing aliases (`manager: { id: "staffs.id", name: "users.name" }`) passes with a single `id`. The group becomes `null` only when that `id` is `null`; fields from other aliases simply stay `null`.
- Groups containing only SQL expressions are not checked and always stay objects. INNER JOIN groups never become `null`.
- Aliases LEFT JOINed from a subquery follow the same rule. To select one as a nested group, the subquery must select `id`.
- For an alias joined outside Puri, such as with `rawQuery().joinRaw()`, a group with `id` becomes null when that `id` is null. A group without `id` is not checked and stays an object.
- To fold a LEFT JOIN group in `GROUP BY` or `DISTINCT` queries, include its `id` in the select and in `GROUP BY`.

```typescript
await puri
  .leftJoin({ detail: "details" }, "roots.id", "detail.root_id")
  .select({ id: "roots.id", detail: { id: "detail.id", note: "detail.note" } });
// detail: null without a match; an object when matched, even if note is null
```

### Subset queries

Subset and loader queries generated by `sonamu sync` now add `id` to every joined relation group that lacks one, and strip it from results like an internal field. Upgrading alone leaves entities unchanged, so `sonamu sync` will not regenerate; run `sonamu sync --force` and commit the result. Without it, LEFT JOIN groups lacking `id` throw at execution. The value is not written to `internal` in entity.json.

As a result, a nullable relation below the second level whose subset does not select `id` now comes back as `null` when empty, rather than an object of `null` fields. Subset and loader queries use Puri's folded results directly and no longer pass through `BaseModel.hydrate()`. Flat `__` aliases appended to a subset query with `appendSelect` are no longer turned into nested objects; select nested objects instead.

### `BaseModel.hydrate()` deprecated

It guesses relation presence from `__` in key names and field values, so an empty group without `id` becomes an object, and `__` inside JSON values or explicit aliases is folded too. Await the Puri query directly instead. The function remains available.

## 0.13.3

### Nested Puri select results

Nested objects passed to `select` or `appendSelect` now produce nested results in standalone Puri queries as well. This applies to `await`, `then`, `catch`, `finally`, and `first`.

```typescript
const rows = await puri.select({ files: { id: "files.id", key: "files.key" } });
// rows[0].files.id, rows[0].files.key
```

If you accessed flat runtime keys such as `files__id`, switch to nested property access. Explicit flat aliases (`{ files__id: "files.id" }`) and keys inside JSON values are not transformed. Subset queries retain their loader-before-hydration order. Existing manual `BaseModel.hydrate()` calls can remain, but calls used only to restore a nested select are no longer necessary. Manual hydration still transforms explicit `__` aliases.

For plain row queries, nested groups matching a LEFT JOIN alias, or whose selected `id` comes from a LEFT JOIN table, use actual row presence. A renamed group such as `manager: { id: "staffs.id" }` follows the source relation. A matched row remains an object even when every selected value is `null`; only an absent row becomes `null`. Arbitrary grouping objects remain objects.

Queries with `GROUP BY`, aggregates, `DISTINCT`, `UNION`, `*`, or SQL expressions do not receive extra presence columns that could change their semantics. In these queries, an explicitly selected `id` is used when available; an all-null group without an ID remains an object. Do not treat an aggregate result group as an individual related record.

### Storage initialization and disk names

With `server.storage` configured, storage is available after `init()` and `initForTesting()`. `createServer()` reuses that manager. Each driver is still created lazily on the first `use()` of its disk.

Disk names are no longer restricted to `fs` and `s3`. Register `drivers: { images: drivers.s3(options) }` and use `Sonamu.storage.use("images")`. `DiskName` is a string; `DriverKey` still identifies the `"fs" | "s3"` factory kinds. Remove `as never` casts added solely for named disks. Unregistered names still throw when passed to `use()`.

## 0.13.0

### Fastify 5

Starting with Sonamu 0.13, the framework runs on Fastify 5 and the matching major versions of
the `@fastify/*` plugins. Fastify and its plugins are dependencies of `sonamu`, so bumping
`sonamu` and re-running `pnpm install` upgrades them together. If your project declares
`fastify` directly, align it to `^5` or remove it.

Everything Sonamu provides (`@api`, `@websocket`, `@stream`, auth, file upload, and so on)
works without code changes. Review the three places below only if your project uses them
directly.

<Steps>
  <Step title="server.plugins.ws.errorHandler">
    From `@fastify/websocket` 11, the second argument is the `ws.WebSocket` instance instead
    of a `{ socket }` wrapper. Replace `connection.socket` with `socket`.
  </Step>
  <Step title="server.plugins.custom, lifecycle.onError">
    Fastify 4-only APIs (`request.routerPath`, `reply.context`, `reply.getResponseTime()`,
    the `reply.redirect(code, url)` argument order, and others) were removed or changed. See
    the Fastify 5
    [migration guide](https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/). The
    `server.fastify` option no longer accepts `logger`; Sonamu configures the logger through
    `loggerInstance`.
  </Step>
  <Step title="request.hostname">
    In Fastify 5, `request.hostname` no longer includes the port. Use `request.port` or
    `request.headers.host` when you need it.
  </Step>
</Steps>

### Peer dependency changes

These `sonamu` peer dependency ranges changed in 0.13.0. Align the catalog in your project’s
`pnpm-workspace.yaml` to the same ranges.

| Package | Before | 0.13.0 | What to check |
| --- | --- | --- | --- |
| `better-auth`, `@better-auth/*` | `~1.6` | `~1.7` | `twoFactor.enable()` now returns a union discriminated by `method`; `totpURI` and `backupCodes` exist only when `method === "totp"`. |
| `zod` | `^4.3` | `^4.6` | Required by better-auth 1.7. Two installed copies of zod cause type errors, so align the catalog, then run `pnpm dedupe`. |
| `ioredis` | `^5` | `^6` | Sonamu’s cache and WebSocket adapters work without code changes. If you use ioredis directly, see the [ioredis 6 release notes](https://github.com/redis/ioredis/releases). |
| `knex` | `^3.2` | `^3.3` | None |
| `pgvector` | `^0.2` | `^0.3` | None |
| `voyageai` | `^0.0.8` | `^0.4` | None. Sonamu only calls `VoyageAIClient.embed()`. |
| `ai` | `^6` | `^7` | `StreamTextResult`, the return type of `streamText()`, now takes three type arguments; if you spell it out, use `StreamTextResult<Tools, Context, Output>`. `toUIMessageStreamResponse().headers` is a `Headers` instance, so read it with `headers.entries()`, not `Object.entries()`. |
| `@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/provider` | `^3` | `^4` | Custom providers written against the V3 specs (`ProviderV3`, `TranscriptionModelV3`, and so on) keep working. |
| `@ai-sdk/provider-utils` | `^4` | `^5` | `ToolExecutionOptions` is now generic: `ToolExecutionOptions<Context>`. |

`fastify` is covered in the Fastify 5 section above. All other peer ranges are unchanged.

The template project’s dev dependencies moved as well. `vitest` 5 (with `@vitest/coverage-v8`)
enables `clearMocks` by default, so tests that rely on mock call history from earlier tests
will fail. `vite` 8.3 and `dotenv` 18 need no attention.

### Projects generated with create-sonamu

A generated project’s `pnpm-workspace.yaml` pins `seroval` to `1.4.2`. That version has a
deserialization vulnerability, so change the override to:

```yaml pnpm-workspace.yaml
overrides:
  seroval: ^1.6.11
  seroval-plugins: 1.5.6
```

`web/tsconfig.node.json` typechecks `vite.config.ts`, and the Vite plugins’ type declarations
reference optional bundlers that are not installed (`webpack`, `rollup`, and others), which makes
the web typecheck step of `sonamu build` fail. Add `skipLibCheck`, as `tsconfig.app.json` already does:

```json web/tsconfig.node.json
{
  "compilerOptions": {
    "composite": true,
    "module": "ESNext",
    "moduleResolution": "bundler",
    "allowSyntheticDefaultImports": true,
    "strict": true,
    "skipLibCheck": true,
    "types": ["node"]
  },
  "include": ["vite.config.ts"]
}
```

Upgrading TanStack Router to `1.170.45` or later is also recommended. The 1.170 generator rewrites
`routeTree.gen.ts` in a new format; commit that change after the first `sonamu dev` run.

Newly generated projects already include both changes.
