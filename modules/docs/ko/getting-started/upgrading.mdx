## 0.13.12

### 인증 secret 필수

auth를 쓰는 서버는 test를 뺀 모든 환경(development, staging, production)에서 secret이 없거나 공개된 값이면 기동하지 않습니다. `openssl rand -base64 32`로 환경마다 값을 만들어 `BETTER_AUTH_SECRET`(또는 `server.auth.secret`)에 넣으세요. 이전 예시의 fallback(`"miomock-secret-key-change-this-in-production"`) 같은 공개 값으로 운영했다면 secret을 교체하고 기존 세션을 폐기하세요. `secrets`·`BETTER_AUTH_SECRETS`로 키를 교체하는 중이라면 남아 있는 공개된 이전 키도 지워야 합니다. `init()`만 하는 `sync`·`migrate` 같은 CLI 작업은 검사하지 않습니다.

### 2FA 사용자는 이메일 인증으로 로그인되지 않음

2FA를 켠 사용자에게 `/api/auth/verify-email`이 새로 발급한 세션(`autoSignInAfterVerification` 포함)은 이제 바로 폐기됩니다. 이메일 인증·변경은 그대로 반영됩니다. 인증 직후 로그인된 상태를 가정하는 화면이 있다면 일반 로그인으로 보내세요.

### `user.additionalFields`의 `input` 기본값은 `false`

`input`을 지정하지 않은 `user.additionalFields` 필드는 이제 가입(`/api/auth/sign-up/email`)·수정(`/api/auth/update-user`) 요청 바디로 받지 않습니다. 이런 필드를 요청에 넣으면 가입 시 `defaultValue`가 있을 때는 무시되고, 그 밖에는 400 `FIELD_NOT_ALLOWED`로 실패합니다. 클라이언트가 직접 넣어야 하는 필드에만 `input: true`를 명시하고, `role` 같은 권한 필드에는 쓰지 마세요. 자세한 내용은 [인증 설정](/ko/api-development/authentication/setup)을 참고하세요.

### 인증 정보 Entity의 Model 스캐폴드 거부

better-auth가 인증 정보를 저장하는 Entity(`Session`, `Account`, `Verification`, `TwoFactor`, `Passkey`, `Jwks`, `ApiKey`, `SsoProvider`)는 CLI와 Sonamu UI 모두 Model 스캐폴드를 거부합니다. 업그레이드해도 이미 만든 Model과 entity.json의 subset은 그대로이므로 직접 정리하세요.

- 스캐폴드로 만든 이 Entity의 Model API는 지우거나, 꼭 필요한 메서드에만 관리자 가드를 거세요.
- subset에서 비밀 필드(`Session.token`, `Account`의 `access_token`·`refresh_token`·`id_token`·`password`, `Verification.value`, `TwoFactor`의 `secret`·`backup_codes`, `Jwks.private_key`, `ApiKey.key`, `SsoProvider`의 `oidc_config`·`saml_config`)를 빼고 `sonamu sync`를 실행하세요.

### 원격 환경의 인증 baseURL 필수

staging·production에서 auth를 쓰면 `server.auth.baseURL`, `BETTER_AUTH_URL` 같은 better-auth 환경 변수, 절대 http(s) URL인 `server.baseUrl` 중 하나가 있어야 서버가 기동합니다. 비밀번호 재설정·이메일 인증 링크를 요청의 `Host` 헤더로 만들지 않기 위해서입니다. `` baseURL: process.env.BETTER_AUTH_URL ?? `http://${host}:${port}` ``처럼 로컬 주소를 fallback으로 둔 설정은 이 검사를 통과하지만 배포 환경에서 잘못된 링크를 만드니, 배포할 때 `BETTER_AUTH_URL`을 꼭 설정하세요.

### `NODE_ENV`가 없을 때의 환경 판정

런타임 `NODE_ENV`가 없으면 이제 `.env.local`, `.env`에 적힌 `NODE_ENV`를 먼저 보고, 그것도 없을 때만 기본값을 씁니다. `sonamu build`·`sonamu start`와 `createServer()`로 띄운 서버의 기본값은 `development`에서 `production`으로 바뀌었습니다. `sonamu dev`와 테스트, CLI 도구는 계속 `development`입니다.

- `NODE_ENV` 없이 띄우던 개발·staging 서버는 `NODE_ENV`를 명시하세요. 그대로 두면 production 설정과 DB preset을 쓰며, `.env`와 `.env.production`이 모두 없으면 기동하지 않습니다.
- `.env`나 `.env.local`에 `NODE_ENV`를 적어 두었다면 `sync`·`migrate` 같은 CLI 도구도 그 환경을 씁니다. 예를 들어 `.env`에 `NODE_ENV=production`이 있으면 `migrate run`은 production DB를 대상으로 합니다.

### 가드 없는 상태 변경 API 경고와 `guardKeys`

GET·HEAD·OPTIONS가 아닌 API에 `guards`가 없으면 서버 시작 시 경고가 출력됩니다. 의도한 공개 API에는 `guards: []`를 지정하고, 나머지에는 알맞은 가드를 거세요. 새 옵션 `server.apiConfig.guardKeys`에 `guardHandler`가 실제로 검사하는 키를 적으면 목록 밖 키는 `guardHandler`를 거치지 않고 401로 거부되며, 그런 키를 쓰는 API가 있으면 서버가 시작되지 않습니다. 설정하지 않으면 기존처럼 모든 키를 `guardHandler`에 넘기므로 핸들러가 검사하지 않는 키는 통과합니다. 자세한 내용은 [서버 설정](/ko/configuration/sonamu-config/server)을 참고하세요.

### 비동기 가드를 기다리고 `false` 반환을 거부로 처리

이제 `guardHandler`가 반환한 Promise를 기다린 뒤 다음 가드와 API를 실행하고, `false`를 반환하면 `UnauthorizedException`(401)으로 거부합니다. 이전에는 async 가드의 거부와 `false` 반환이 무시되어 요청이 그대로 실행됐으므로, 이 동작에 기대던 가드가 있다면 이제 요청을 막는지 확인하세요. `lifecycle.onError`를 직접 구현했다면 `isSoException(error) ? error.statusCode : 500`처럼 Sonamu 예외의 상태 코드를 유지하세요. 모두 500으로 응답하면 가드 거부도 500이 됩니다.

### 새 프로젝트의 기본 거부 `guardHandler`

`create-sonamu`로 만드는 새 프로젝트의 `guardHandler`는 기본 거부 방식입니다. `user`는 로그인하지 않았으면 401, `admin`은 로그인하지 않았거나 관리자가 아니면 403, 판정 로직이 없는 `query`와 커스텀 키는 403으로 거부합니다. 기존 프로젝트의 설정은 바뀌지 않으므로, 예전 템플릿처럼 로그만 남기거나 처리하지 않는 키를 그냥 통과시키는 `guardHandler`는 같은 방식으로 바꾸세요. 403에는 프로젝트에서 정의한 `ForbiddenException`을 쓰세요. 자세한 내용은 [인증 설정](/ko/api-development/authentication/setup)을 참고하세요.

### `BaseSaveParams`와 스캐폴드 `save`의 관리자 가드

`sonamu.generated.ts`에 엔티티별 `{Entity}BaseSaveParams`가 생깁니다. `created_at`, generated·searchText 컬럼, `readonly: true` prop(관계는 FK)을 뺀 저장 입력 스키마로, sync마다 다시 만들어집니다. 새로 스캐폴드한 `SaveParams`는 이를 기반으로 하고, `save` API에는 `guards: ["admin"]`이 붙습니다. 기존 프로젝트의 `*.types.ts`와 모델은 바뀌지 않으므로 직접 옮기세요.

- 권한·인증 상태·비밀값 prop에 `readonly: true`를 지정하세요. 기존 better-auth 엔티티의 entity.json에도 자동으로 추가되지 않습니다.
- `SaveParams`를 `{Entity}BaseSaveParams.partial({ id: true })`로 바꾸고 `sonamu sync`를 실행하세요. 저장 입력이나 폼에서 `created_at`을 쓰던 곳은 조회한 행의 값을 쓰게 고치세요.
- 스캐폴드한 `save`를 비롯한 쓰기 API의 `guards`를 확인하세요.

### `sonamuFilter`는 `toFilter` prop만 허용

`sonamuFilter`는 이제 entity.json에서 `"toFilter": true`로 지정한 prop만 필터링합니다. 관계의 FK(`{관계명}_id`)는 관계 prop에 지정해야 하고, 허용하지 않은 필드나 잘못된 연산자·값은 쿼리 전에 `BadRequestException`(400)으로 거부됩니다. 서버 코드에서 `findMany`를 호출할 때도 같습니다. 필터에 쓰는 필드에만 `toFilter: true`를 지정하고 `sonamu sync`를 실행하세요. 비밀번호·토큰 같은 비밀 필드는 지정하지 마세요. 자세한 내용은 [sonamuFilter](/ko/api-reference/base-model/sonamu-filter)를 참고하세요.

### SSR preload에 가드와 입력 검증 적용

SSR preload도 이제 API의 `guards`와 HTTP 입력 검증을 거칩니다. 가드가 거부하면 해당 preload를 건너뛰므로, 가드를 통과하지 못한 방문자의 HTML에는 그 데이터가 미리 채워지지 않습니다. 가드를 통과한 preload의 인자가 검증에 실패하면(예: `parseInt`가 만든 `NaN`) 페이지 전체가 400으로 응답하므로, URL 파라미터를 변환해 넘기는 preload를 점검하세요. 자세한 내용은 [데이터 프리로딩](/ko/frontend-integration/ssr/preloading-data)을 참고하세요.

### 인라인 객체 파라미터 안의 명명 타입 검증

`params: { data: UserSaveParams }`처럼 인라인 객체 파라미터 안에 둔 명명 타입은 이전에는 검증 없이 통과했지만, 이제 최상위 파라미터와 같은 Zod 스키마로 검증합니다. 잘못된 값은 400으로 거부되고 스키마에 없는 키는 제거되므로, 이런 파라미터에 스키마 밖의 값을 넣어 보내던 클라이언트와 그 값에 기대던 모델 코드를 점검하세요.

### `null`·`undefined`·불리언 리터럴이 섞인 파라미터 검증

API 파라미터 타입의 `null`, `undefined`, `void`, `true`, `false`는 이전에 아무 값이나 통과시켰고, 이런 멤버가 섞인 union(예: `"asc" | "desc" | null`)도 전체가 검증되지 않았습니다. 이제 각 타입에 맞는 값만 받고 나머지는 400으로 거부합니다. GET 파라미터를 `true | false` union으로 선언했다면 쿼리 문자열이 불리언으로 바뀌지 않아 거부되므로 `boolean`으로 바꾸세요. GET에서 `number`가 섞인 union은 쿼리 문자열을 숫자로 바꾼 뒤 검증하므로 숫자가 아닌 문자열은 거부됩니다.

### `tools/openVscode`의 `absPath` 제한

Sonamu UI API `tools/openVscode`는 이제 `absPath`로 앱 루트(API 디렉토리의 상위 디렉토리) 아래에 실제로 있는 파일만 엽니다. 앱 루트 밖 경로와 그곳을 가리키는 심볼릭 링크, 디렉토리, 없는 파일은 400으로 거부합니다. UI의 파일 열기 버튼은 그대로 동작하므로, 이 API로 다른 위치의 파일을 열던 스크립트만 고치면 됩니다.

### 에디터 실행 API는 JSON POST만 받음

`tools/openVscode`와 `tools/openEditor`는 GET 쿼리 대신 JSON 본문의 POST로 호출해야 합니다. 이 둘과 `cdd/openSource`, `cdd/editContent`는 `Content-Type: application/json`과 `X-Sonamu-UI: 1` 헤더가 없거나 다른 출처에서 온 요청을 403으로 거부합니다. 번들된 UI는 이미 이렇게 호출하므로 직접 호출하던 스크립트만 바꾸면 됩니다.

### Sonamu UI API 접근 토큰과 DevRunner 요청 검사

`/sonamu-ui/api/**`는 이제 서버가 프로세스마다 만드는 접근 토큰을 `X-Sonamu-UI-Token` 헤더로 받아야 하며, 토큰이 없거나 틀리면 401, 다른 출처에서 온 요청이면 403입니다. UI는 `/sonamu-ui` HTML에 든 토큰을 자동으로 보내므로 평소처럼 접속하고, 서버를 재시작한 뒤에는 새로고침하세요. UI API를 직접 호출하던 도구는 그 HTML의 `sonamu-ui-token` meta 태그에서 토큰을 읽어 보내야 합니다. DevRunner(기본 `/__test__`)는 토큰 대신 다른 출처 요청을 403, JSON이 아닌 POST를 415로 거부하며 `sonamu test`는 그대로 동작합니다. 자세한 내용은 [Sonamu UI 시작하기](/ko/tools-and-cli/sonamu-ui/getting-started)를 참고하세요.

### Sonamu UI·DevRunner의 Host 검사

로컬 개발 서버의 Sonamu UI와 DevRunner는 이제 `Host`가 `localhost`, `*.localhost`, IP 주소, `server.listen.host`·`server.baseUrl`의 호스트 이름이 아닌 요청을 403으로 거부합니다. `/etc/hosts` 별칭이나 터널 도메인으로 접속해 왔다면 그 호스트 이름을 `server.listen.host`나 `server.baseUrl`에 지정하세요. 별도의 허용 목록 옵션은 없고, `0.0.0.0` 바인딩으로는 이 검사를 끌 수 없습니다. 앱 API는 검사하지 않습니다.

### Sonamu UI의 DB 대상 제한과 롤백 승인

Sonamu UI는 이제 `development`·`test`·`fixture` 계열 프리셋만 다룹니다. `staging`·`production` 대상의 마이그레이션 적용·롤백과 fixture 조회·가져오기는 400으로 거부되므로 `sonamu migrate` 같은 CLI로 옮기세요. UI에서 다시 허용하는 옵션은 없습니다. Slack 승인 대상인 원격 DB는 UI 롤백에도 승인이 필요하며, 승인은 대상과 최신 batch마다 따로 받습니다. 승인 요청 API를 직접 호출한다면 롤백에는 `action: "rollback"`을 지정하세요(생략하면 `apply`). 자세한 내용은 [프로덕션 승인](/ko/database/migrations/production-approval)을 참고하세요.

### entity.json의 코드 생성 값 검사

생성 코드에 들어가는 entity.json 값을 이제 로드·저장·코드 생성 때 검사합니다. Entity `id`·`parentId`·`table`, prop `name`, enum ID, 관계의 `with`·`relationType`·`joinTable`·`joinColumn`·`fromColumn`은 ASCII 식별자(`^[A-Za-z_$][A-Za-z0-9_$]*$`)여야 하고, prop의 `id`와 subset 키·필드 경로도 비슷한 형식을 따라야 합니다. `length`·`precision`·`scale`·`dimensions`는 문자열이 아닌 숫자, `zodFormat`은 지원하는 값이어야 합니다. 검사에 실패하면 경고만 남기던 이전과 달리 서버 기동과 `sonamu sync`가 멈추고 Sonamu UI 저장은 400으로 거부됩니다. 한글처럼 JavaScript가 허용하는 비ASCII 식별자도 거부하므로 오류 메시지에 나온 값을 고치세요. `title`·`desc`와 enum 값의 키·레이블은 제한하지 않습니다.

### 마이그레이션 생성의 SQL 조각 제한

자동 마이그레이션 생성은 이제 SQL 식인 `dbDefault`, `generated.expression`, 인덱스 `where`처럼 SQL로 들어가는 값에 `;`가 있으면 오류를 냅니다. SQL 문자열 리터럴 안의 `;`도 거부하므로, 그런 SQL은 직접 작성한 마이그레이션으로 옮기세요. 큰따옴표로 시작하는 `dbDefault`(문자열 값 기본값)는 큰따옴표 문자열 리터럴 하나여야 하며 뒤에 다른 식을 붙일 수 없습니다. 기존의 `\x5b` 같은 이스케이프는 그대로 쓸 수 있습니다.

### 스캐폴딩 API 입력과 생성 경로 제한

Sonamu UI의 스캐폴딩 API(`scaffolding/getStatus`·`generate`·`preview`)는 이제 등록된 Entity ID와 `model`, `model_test`, `view_list`, `view_search_input`, `view_form`, `view_id_all_select` 템플릿만 받고, 그 밖의 값은 상태 조회에서도 400으로 거부합니다. 또한 템플릿 생성 경로가 앱 루트(API 디렉토리의 상위 디렉토리) 밖을 가리키면 파일을 쓰기 전에 오류가 납니다. `sync.targets`에 `"../frontend/web"`처럼 앱 루트 밖 경로를 썼다면 `sonamu sync`가 실패하므로, target을 앱 루트 안으로 옮기거나 앱 루트 안에 심볼릭 링크를 두고 그 경로를 지정하세요. 자세한 내용은 [동기화 대상](/ko/configuration/sonamu-config/sync-targets)을 참고하세요.

### i18n 함수 값은 허용 목록을 통과해야 함수로 저장됨

Sonamu UI, Excel, CLI로 넣는 사전 값은 이제 허용 목록을 통과하는 화살표 함수 하나일 때만 함수로 저장됩니다. 다른 함수를 부르는 값처럼 그 밖의 함수 형태 값은 문자열로 저장되므로, import 파일에 그런 값이 있다면 그 함수는 사전 TS 파일에 직접 작성하세요. 자세한 규칙은 [함수형 값 처리](/ko/advanced-features/i18n/excel-import#함수형-값-처리)를 참고하세요.

### 요청 처리 DB 풀의 기본 `statement_timeout`과 PostgreSQL 전용 설정 타입

테스트 환경이 아니면 `DB.getDB("w")`·`DB.getDB("r")` 풀에 `statement_timeout` 15초가 기본으로 적용되어, 더 오래 걸리는 쿼리는 PostgreSQL 오류 `57014`로 취소됩니다. 앱 프로세스에서 긴 리포트·배치 쿼리를 실행한다면 `database.defaultOptions.connection.options`로 값을 바꾸거나 트랜잭션 안에서 `SET LOCAL statement_timeout`으로 늘리세요. 또한 `SonamuDBConfig`는 이제 `Record<SonamuDBPreset, DatabaseConfig>`이고 `DB.getDBConfig()`도 `DatabaseConfig`를 반환합니다. `Knex.Config` 타입 값이나 문자열·함수형 `connection`으로 이 설정을 만들던 코드는 컴파일되지 않으므로 `Knex.PgConnectionConfig` 객체를 쓰는 `DatabaseConfig`로 바꾸세요. 자세한 내용은 [데이터베이스 설정](/ko/configuration/sonamu-config/database)을 참고하세요.

### Puri `limit`·`offset`의 정수 검사

`limit`·`offset`은 이제 0 이상의 안전한 정수가 아니면 쿼리 전에 `Error`를 던집니다. 이전에는 `NaN`·`Infinity`를 넘기면 LIMIT 없이 실행됐으므로, 요청 값을 그대로 넘기던 코드는 정수로 바꾸고 검증한 뒤 넘기세요.

## 0.13.10

### 중첩 select의 null 판정은 id로만

일반 Puri 조회가 LEFT JOIN 행이 있는지 보려고 SQL에 몰래 끼우던 존재 확인 컬럼(`"alias".* IS DISTINCT FROM NULL`)을 없앴습니다. 이제 중첩 그룹이 null인지는 그 그룹의 `id`가 null인지로만 판정합니다. 0.13.3 절의 존재 확인 설명은 이 절로 대체됩니다.

- 그룹 이름이 LEFT JOIN 별칭과 같거나, 그룹 칸이 LEFT JOIN 별칭을 가리키는데 그룹에 `id`가 없으면 실행할 때 오류가 납니다. 그 별칭의 `id`를 그룹에 넣거나, 칸을 평평한 별칭(`{ detail__note: "detail.note" }`)으로 고르세요. `rawQuery()`와 `toQuery()`는 검사하지 않습니다.
- 여러 별칭이 섞인 그룹(`manager: { id: "staffs.id", name: "users.name" }`)은 `id` 하나로 통과합니다. 그룹은 그 `id`가 null일 때만 null이 되고, 다른 별칭의 칸은 값이 null로 남습니다.
- SQL 식만 든 그룹은 검사하지 않고 늘 객체로 둡니다. INNER JOIN 그룹은 null이 되지 않습니다.
- 서브쿼리를 LEFT JOIN한 별칭도 같습니다. 중첩 그룹으로 고르려면 서브쿼리가 `id`를 골라 와야 합니다.
- `rawQuery().joinRaw()`처럼 Puri가 모르게 붙인 별칭은 그룹에 `id`가 있으면 그 `id`가 null일 때 null이 됩니다. `id`가 없으면 검사하지 않고 객체로 둡니다.
- `GROUP BY`·`DISTINCT` 조회에서 LEFT JOIN 그룹을 접으려면 그 `id`를 select와 `GROUP BY`에 넣으세요.

```typescript
await puri
  .leftJoin({ detail: "details" }, "roots.id", "detail.root_id")
  .select({ id: "roots.id", detail: { id: "detail.id", note: "detail.note" } });
// 짝이 없으면 detail: null, 짝이 있으면 note가 null이어도 객체
```

### 서브셋 조회

`sonamu sync`가 만드는 서브셋 쿼리와 로더 쿼리는 JOIN으로 붙는 관계 그룹에 `id`가 없으면 자동으로 넣고, 결과에서는 internal 필드처럼 지웁니다. 버전만 올리면 entity가 그대로라 `sonamu sync`가 생성 코드를 다시 만들지 않으니, `sonamu sync --force`로 다시 만들고 커밋하세요. 다시 만들지 않으면 id 없는 LEFT JOIN 그룹이 실행할 때 오류를 냅니다. 이 값은 entity.json의 `internal`에 쓰이지 않습니다.

그래서 서브셋이 `id`를 고르지 않은 둘째 단계 아래 nullable 관계도 비어 있으면 칸이 전부 null인 객체가 아니라 `null`로 나옵니다. 서브셋 본 쿼리와 로더 쿼리는 Puri가 접은 결과를 그대로 쓰며, `BaseModel.hydrate()`를 더 거치지 않습니다. 서브셋 쿼리에 `appendSelect`로 덧붙인 평평한 `__` 별칭은 이제 중첩 객체로 바뀌지 않으니 중첩 객체로 고르세요.

### `BaseModel.hydrate()` deprecated

키 이름의 `__`와 칸 값으로 관계가 있는지 추측해 접으므로, id 없는 그룹은 비어 있어도 객체가 되고 JSON 값이나 직접 지정한 별칭의 `__`도 접어 버립니다. Puri 쿼리를 직접 `await`해 결과를 받으세요. 함수는 아직 남아 있습니다.

## 0.13.3

### 중첩 Puri select 결과

중첩 객체로 `select`·`appendSelect`한 결과는 이제 일반 Puri 조회에서도 자동으로 중첩 객체가 됩니다. `await`, `then`, `catch`, `finally`, `first`에 동일하게 적용됩니다.

```typescript
const rows = await puri.select({ files: { id: "files.id", key: "files.key" } });
// rows[0].files.id, rows[0].files.key
```

이전 런타임 결과의 `files__id` 같은 키를 직접 읽었다면 중첩 프로퍼티 접근으로 바꾸세요. 직접 지정한 평평한 별칭(`{ files__id: "files.id" }`)과 JSON 값 내부의 키는 변환하지 않습니다. 서브셋 조회의 로더와 hydrate 순서는 유지됩니다. 기존 수동 `BaseModel.hydrate()` 호출도 남겨둘 수 있지만, 일반 중첩 select만 복원하기 위해 호출했다면 제거할 수 있습니다. 수동 hydrate 자체는 여전히 직접 지정한 `__` 별칭도 변환합니다.

일반 행 조회에서는 LEFT JOIN 별칭과 일치하는 중첩 그룹, 또는 `id`가 LEFT JOIN 테이블에서 선택된 그룹의 실제 행 존재 여부를 확인합니다. 그룹 이름을 `manager`로 바꾸어도 `id: "staffs.id"`처럼 선택하면 원본 관계를 따릅니다. 따라서 매칭된 행의 선택 값이 모두 `null`이어도 객체를 유지하고, 매칭된 행이 없을 때만 `null`이 됩니다. 임의로 묶은 그룹은 객체로 유지합니다.

`GROUP BY`, 집계, `DISTINCT`, `UNION`, `*` 또는 SQL 표현식이 있는 조회에는 결과 의미를 바꿀 수 있는 존재 확인 컬럼을 추가하지 않습니다. 이 경우 명시적으로 선택한 `id`가 있으면 이를 기준으로 판별하고, ID 없이 모두 `null`인 그룹은 객체로 유지합니다. 집계 결과의 그룹을 개별 관계 레코드로 간주하지 마세요.

### 스토리지 초기화와 디스크 이름

`server.storage` 설정이 있으면 `init()`과 `initForTesting()`에서도 스토리지를 사용할 수 있습니다. `createServer()`는 이미 생성한 매니저를 재사용합니다. 드라이버는 해당 디스크의 첫 `use()` 때 생성됩니다.

디스크 이름은 `fs`·`s3`에 제한되지 않습니다. `drivers: { images: drivers.s3(options) }`로 등록하고 `Sonamu.storage.use("images")`로 사용하세요. `DiskName`은 문자열이고, `DriverKey`는 드라이버 팩토리 종류인 `"fs" | "s3"`를 유지합니다. 이름 때문에 추가한 `as never` 캐스팅은 제거할 수 있습니다. 등록하지 않은 이름은 `use()`에서 오류를 냅니다.

### Fastify 5

Sonamu 0.13부터 Fastify 5와 그에 맞는 `@fastify/*` 플러그인 메이저 버전을 사용합니다. Fastify와
플러그인은 `sonamu`의 의존성이므로 `sonamu`를 올리고 `pnpm install`을 다시 실행하면 함께
갱신됩니다. 프로젝트가 `fastify`를 직접 의존성으로 선언했다면 `^5`로 맞추거나 제거하세요.

`@api`, `@websocket`, `@stream`, 인증, 파일 업로드 등 Sonamu가 제공하는 기능은 코드를 바꾸지
않아도 그대로 동작합니다. 다음 세 곳을 직접 사용했다면 확인이 필요합니다.

<Steps>
  <Step title="server.plugins.ws.errorHandler">
    `@fastify/websocket` 11부터 두 번째 인자가 `{ socket }` 래퍼가 아닌 `ws.WebSocket`
    인스턴스입니다. `connection.socket`을 `socket`으로 바꾸세요.
  </Step>
  <Step title="server.plugins.custom, lifecycle.onError">
    Fastify 4 전용 API(`request.routerPath`, `reply.context`, `reply.getResponseTime()`,
    `reply.redirect(code, url)` 인자 순서 등)는 제거되거나 바뀌었습니다. Fastify 5
    [마이그레이션 가이드](https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/)를 참고하세요.
    `server.fastify` 옵션에는 더 이상 `logger`를 넣을 수 없습니다. Sonamu가 `loggerInstance`로
    로거를 설정합니다.
  </Step>
  <Step title="request.hostname">
    Fastify 5의 `request.hostname`에는 포트가 포함되지 않습니다. 포트가 필요하면 `request.port`
    또는 `request.headers.host`를 사용하세요.
  </Step>
</Steps>

### create-sonamu로 생성한 프로젝트

생성된 프로젝트의 `pnpm-workspace.yaml`은 `seroval`을 `1.4.2`로 고정합니다. 이 버전에는
역직렬화 취약점이 있으므로 다음과 같이 바꾸세요.

```yaml pnpm-workspace.yaml
overrides:
  seroval: ^1.6.11
  seroval-plugins: 1.5.6
```

`web/tsconfig.node.json`은 `vite.config.ts`를 검사하는데, Vite 플러그인의 타입 선언이 설치되지 않은
선택적 번들러(`webpack`, `rollup` 등)를 참조해 `sonamu build`의 web 타입 검사가 실패합니다.
`tsconfig.app.json`과 같이 `skipLibCheck`를 추가하세요.

```json web/tsconfig.node.json
{
  "compilerOptions": {
    "composite": true,
    "module": "ESNext",
    "moduleResolution": "bundler",
    "allowSyntheticDefaultImports": true,
    "strict": true,
    "skipLibCheck": true,
    "types": ["node"]
  },
  "include": ["vite.config.ts"]
}
```

TanStack Router를 `1.170.45` 이상으로 올리는 것도 권장합니다. 1.170 generator는 `routeTree.gen.ts`를
새 형식으로 다시 쓰므로 첫 `sonamu dev` 실행 뒤 그 변경을 커밋하면 됩니다.

새로 생성하는 프로젝트에는 두 변경이 이미 적용되어 있습니다.
