인덱스를 만들고, 정의가 바뀌면 다시 만들고, 읽기 포인터를 옮기고, 옛 인덱스를 지우는 일은 모두 운영자가 명시적으로 실행하는 관리 명령입니다. 서버 시작이나 워커는 이 일을 하지 않습니다. 이 페이지는 `createSearchAdmin`이 만드는 관리 핸들의 작업을 쓰는 순서대로 다루고, 셸에서 그 작업을 실행하는 `sonamu search` 명령도 설명합니다. 문제가 생긴 대상을 되살리는 절차와 복사하거나 복원한 데이터베이스를 다루는 절차는 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)에 있습니다.

## 관리 핸들

관리 핸들은 `@sonamu-kit/opensearch/admin`의 `createSearchAdmin`으로 만들고, 관리자 자격 증명을 씁니다. PostgreSQL admin 역할과, 인덱스를 만들고 지울 수 있는 OpenSearch 사용자입니다. 런타임 프로세스에는 이 자격 증명을 주지 마세요.

```typescript title="search/administration.ts"
/** Build the admin handle with admin credentials only, and run its commands explicitly from operator tooling. */
export function createChatSearchAdmin(adminDatabase: () => Knex): SearchAdmin {
  return createSearchAdmin({
    ...adminOptions(adminDatabase),
    client: createSearchClient({
      createClient: () =>
        new Client({ node: process.env.OPENSEARCH_ADMIN_URL ?? "http://localhost:9200" }),
      ownsClient: true,
      requestTimeoutMs: RECOMMENDED_CLIENT_REQUEST_TIMEOUT_MS,
    }),
  });
}

/** Without OpenSearch credentials only POSTGRES_ONLY_ADMIN_OPERATIONS work; the rest refuse with search-client-not-configured. */
export function createChatSearchMonitor(adminDatabase: () => Knex): SearchAdmin {
  return createSearchAdmin(adminOptions(adminDatabase));
}

function adminOptions(adminDatabase: () => Knex): SearchAdminOptions {
  return {
    synchronization: createPostgresSynchronization({
      getPrimaryDatabase: adminDatabase,
      namespace: SEARCH_NAMESPACE,
      // Set a distinct name per environment from its configuration; a name fixed in code protects nothing.
      instanceName: process.env.SEARCH_INSTANCE_NAME,
    }),
    definitions: [chatMessagesSearch],
    lifetimes: RECOMMENDED_ADMIN_LIFETIMES,
    timeouts: RECOMMENDED_ADMIN_TIMEOUTS,
    cutover: RECOMMENDED_CUTOVER,
    // Derive from the limits the workers actually use; retirement waits for in-flight writes by these bounds.
    workerBounds: workerBoundsFrom(RECOMMENDED_WORKER_LIMITS),
  };
}
```

`instanceName`은 환경마다(운영, 스테이징, 개발자 복사본) 그 환경의 설정에서 넣습니다. 코드에 고정한 이름은 모든 환경에서 같으므로 아무것도 막지 못합니다. 이 이름이 하는 일은 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)의 "환경 이름"에 있습니다.

| 옵션 | 뜻 | 권장값 |
| --- | --- | --- |
| `client` | 관리자 자격 증명의 클라이언트. 생략할 수 있습니다(아래) | |
| `synchronization` | namespace, 스키마, primary, `instanceName`을 정하는 동기화 핸들 | |
| `definitions` | 관리할 정의. cutover와 rollback은 양쪽 대상의 정의가 여기에 있어야 합니다 | |
| `lifetimes` | 읽기 수명 최대치와 은퇴 안전 여유. 처음 대상을 만들 때 `read_heads`에 기록됩니다 | `RECOMMENDED_ADMIN_LIFETIMES` |
| `timeouts` | 잠금, 문장, 유휴 트랜잭션 제한 시간과 관리 임대 길이 | `RECOMMENDED_ADMIN_TIMEOUTS` |
| `cutover` | cutover를 허용하는 최대 대기 수(`maxPendingDocuments`)와 표본 검증 크기(`sampleSize`) | `RECOMMENDED_CUTOVER` |
| `workerBounds` | 워커의 `leaseDurationMs`, `requestTimeoutMs`. 워커가 실제로 쓰는 한도에서 가져오며, 은퇴가 기다리는 시간을 정합니다 | `workerBoundsFrom(워커 한도)` |

핸들은 받은 클라이언트를 닫지 않습니다. 클라이언트를 만든 쪽이 닫습니다.

`client`를 생략한 핸들은 OpenSearch에 아무것도 보내지 않는 작업만 실행합니다. 내보낸 `POSTGRES_ONLY_ADMIN_OPERATIONS`에 든 작업(`inspect`, `inspectBuild`, `runBackfillPage`, `suspendCapture`, `remark`, `retryQuarantined`, `adoptCopiedStore`, `changeReadLifetimes`)과, `requiredPlugins`가 없는 정의의 `planCreate`입니다. 나머지 작업은 아무것도 읽거나 쓰기 전에 `SearchAdminPreconditionFailed`(`search-client-not-configured`)로 거부합니다. `confirmStoreOwnership`은 대상의 fence를 되찾으려고 OpenSearch에 쓰므로 목록에 없습니다. 클라이언트가 없으면 원격 인덱스가 있을 수 있는 대상(`creating`, `active`, `paused`, `retiring`)이 하나도 없을 때만 실행됩니다. 모니터링이나 표시 복구처럼 OpenSearch 자격 증명이 필요 없는 도구에는 클라이언트 없는 핸들을 쓰세요. 위의 `createChatSearchMonitor`가 그 예입니다.

워커와 원격 요청을 보내는 모든 작업은 먼저 저장소 결속을 확인합니다. 이 데이터베이스가 저장소가 기록된 그 데이터베이스가 아니거나 `instanceName`이 기록된 이름과 다르면, 아무것도 보내지 않고 `SearchStoreMismatch`로 거부합니다. cutover와 rollback(옮겨 갈 대상), `resumeTarget`, `retireTarget`은 이 데이터베이스가 그 대상의 fence를 아직 가지고 있는지도 확인합니다. 잃었으면 아무것도 바꾸지 않고 `SearchStoreMismatch`(`target-fence-lost`, `details`에 `targetId`, `class`, `localEpoch`, `remoteEpoch`)로 거부합니다. fence를 읽지 못하면 재시도할 수 있는 `SearchUnavailable`(`fence-unreadable`)입니다. 표시, `initialize()`, 검색은 막지 않습니다. 복사본이나 제자리 복원에서 할 일은 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)에 있습니다.

상태를 바꾸는 메서드는 감사 문맥 `{ operationId, actor, reason }`을 받아 `admin_operations`에 시작, 성공, 실패를 기록합니다. 비밀 값을 넣지 마세요.

```typescript title="search/administration.ts"
export function auditContext(actor: string, reason: string): AdminContext {
  return { operationId: `chat-search-${Date.now()}`, actor, reason };
}
```

## 관리 임대

logical key 하나에는 한 번에 관리 작업 하나만 돕니다. 작업은 시작할 때 임대를 얻고, 진행하는 동안 연장하고, 성공하든 실패하든 끝에서 반납합니다. 같은 `operationId`로 다시 부르면 같은 임대를 다시 씁니다.

- `SearchAdminBusy`(`retryable`): 다른 작업이 임대를 쥐고 있거나(`lease-held`), 잠금이나 문장이 제한 시간 안에 끝나지 않았습니다. 잠시 뒤 다시 실행합니다.
- `SearchAdminLeaseLost`(`retryable`): 작업 도중 임대가 만료됐거나 다른 작업에 넘어갔고, 그 뒤의 데이터베이스 쓰기는 하나도 반영되지 않았습니다. 같은 작업을 다시 실행하면 멈춘 곳에서 이어 갑니다.
- 관리 프로세스가 죽으면 `adminLeaseMs`가 지나야 다른 작업이 임대를 가져갈 수 있습니다.

임대는 데이터베이스 쓰기를 막을 뿐, 이미 보낸 원격 명령을 되돌리지 못합니다. 그래서 원격 요청을 보내는 작업(대상 생성, 생성 조정, 캡처 재개, cutover와 rollback, 은퇴, 일시 정지된 대상의 검증과 재개)은 요청 하나의 제한 시간을 임대 안에 들어가게 정합니다.

> 요청 하나의 제한 시간 = (`adminLeaseMs` − 4 × `statementTimeoutMs`) / 3

이 값이 1초보다 작으면 아무것도 보내거나 쓰기 전에 `SearchConfigurationError`(`admin-lease-too-short`)로 거부합니다. 권장값이면 (5분 − 4 × 30초) / 3 = 1분이고, 클라이언트의 `requestTimeoutMs`(30초)가 더 짧으므로 그쪽이 적용됩니다.

## CLI로 관리 명령 실행하기

`@sonamu-kit/opensearch/sonamu`는 관리 작업을 `sonamu` CLI의 플러그인인 `sonamu search` 명령으로 제공합니다. 명령은 애플리케이션이 주는 설정으로 관리 핸들을 만들고, `SearchAdmin` 작업을 하나 이상 실행한 뒤 결과를 출력합니다. 셸에서 하는 운영 작업에는 명령을 쓰세요. 명령에 없는 단계(`changeReadLifetimes`, `planCreate`와 `executeCreate`를 따로 실행하기 등)가 필요하거나 단계 사이에 직접 확인을 넣어야 하면 코드에서 `SearchAdmin`을 부릅니다. 이 페이지와 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)의 임대, 거부, 절차는 양쪽에 똑같이 적용됩니다. CLI가 플러그인을 불러오는 방식은 [CLI 레퍼런스](/ko/tools-and-cli/sonamu-cli/reference)의 "CLI 플러그인"에 있습니다.

### 플러그인 등록

`sonamu.config.ts`의 `cli.plugins`에 플러그인을 넣고, 설정은 별도 모듈에서 만듭니다.

```typescript title="sonamu.config.ts"
  cli: {
    // Loaded lazily, so evaluating this config never imports the search setup.
    plugins: [
      createSearchCliPlugin({
        load: async () => (await import("./search/cli-setup")).chatSearchCliSetup(),
      }),
    ],
  },
```

```typescript title="search/cli-setup.ts"
/** Imported by sonamu.config.ts only when a `sonamu search` command runs. */
export function chatSearchCliSetup(): SearchCliSetup {
  return {
    // During a rebuild, list the new definition first and keep the old one until its target is retired.
    definitions: [chatMessagesSearch],
    synchronization: searchSynchronization,
    // Admin credentials; the plugin creates a client per command and closes it.
    client: () => ({
      createClient: () =>
        new Client({ node: process.env.OPENSEARCH_ADMIN_URL ?? "http://localhost:9200" }),
      ownsClient: true,
      requestTimeoutMs: RECOMMENDED_CLIENT_REQUEST_TIMEOUT_MS,
    }),
    // The same values as the application's admin handle and query handles.
    admin: {
      lifetimes: RECOMMENDED_ADMIN_LIFETIMES,
      timeouts: RECOMMENDED_ADMIN_TIMEOUTS,
      cutover: RECOMMENDED_CUTOVER,
    },
    // The worker's limits (examples/search/worker.ts); retirement waits by them.
    workerLimits: RECOMMENDED_WORKER_LIMITS,
  };
}
```

`load`는 명령마다 `Sonamu.init` 뒤에 실행됩니다. 위처럼 설정 모듈을 지연 import해서, `sonamu.config.ts`를 평가할 때는 검색 모듈을 하나도 불러오지 않게 하세요. `createSearchCliPlugin`은 설정 파일을 평가할 때 옵션을 확인하고(`invalid-cli-options`), 설정 객체는 명령을 실행할 때마다 확인합니다. 형식이 맞지 않으면 `SearchConfigurationError`(`invalid-cli-setup`, 문제가 된 필드는 `details.path`)로 실패합니다.

| 설정 필드 | 용도 |
| --- | --- |
| `definitions` | 아직 서비스하는 모든 정의. logical key마다 지금 정의를 맨 앞에 둡니다. 워커가 받는 목록과 같습니다. 재구축 중에는 옛 대상을 은퇴시킬 때까지 옛 정의를 남겨 두세요. 명령이 받아들이는 logical key는 이 정의들의 key입니다 |
| `synchronization` | 애플리케이션의 동기화 핸들(namespace, 스키마, `instanceName`). 플러그인은 이것을 닫지 않습니다 |
| `client` | 선택. 관리자 자격 증명을 쓰는 클라이언트의 옵션을 돌려주는 함수입니다. 아래 표에 표시한 명령만 이 함수를 부르며, 플러그인은 명령마다 클라이언트를 하나 만들고 명령이 끝나면 닫습니다. `client`를 생략하면 OpenSearch가 필요한 작업을 하는 명령은 `search-client-not-configured`로 거부합니다. 함수가 예외를 던지면(예: URL이 없음) 표시한 명령은 모두 그 오류로 실패하고 나머지는 그대로 실행됩니다 |
| `admin` | `lifetimes`, `timeouts`, `cutover`. 애플리케이션의 관리 핸들과 같은 값을 줍니다. `lifetimes`는 첫 대상과 함께 기록됩니다 |
| `workerLimits` | 워커가 실제로 쓰는 한도. 핸들의 `workerBounds`를 여기서 만들므로 은퇴가 진행 중인 쓰기를 제대로 기다리고, `drain`도 이 한도로 워커를 돌립니다 |

CLI는 빌드된 코드를 실행합니다. 플러그인은 `dist/sonamu.config.js`에서 읽고, `load`는 빌드된 설정 모듈을 import합니다. 플러그인을 등록한 뒤와 설정 모듈이나 정의를 바꿀 때마다 `sonamu build`를 실행하세요. 그러지 않으면 `init`이 옛 정의로 계획합니다. 빌드하지 않았으면 `search`는 알 수 없는 명령(종료 코드 2)이 되고, 오류가 플러그인 명령을 불러오지 못한 이유를 알려 줍니다.

### 명령

`pnpm sonamu search <command> [logicalKey] [options]`. 옵션 값은 `--option value`로 주고, `--ids`는 ID 하나마다 플래그를 반복합니다(`--ids 3 --ids 7`).

| 명령 | 인자와 옵션 | 상태 변경 | `client` 호출 | `SearchAdmin` 작업 |
| --- | --- | --- | --- | --- |
| `inspect` | `[logicalKey]` | 없음 | 아니요 | `inspect`와 저장소 결속. 등록되지 않은 key에도 결속을 보여 줍니다 |
| `init` | `[logicalKey] [--limit N]` | 있음. `--execute`가 없으면 dry run | 예, dry run도 | 등록되지 않은 key면 `planCreate`와 `executeCreate`, 그다음 `beginRebuild`. 첫 빌드면 `runBackfillPage`를 끝까지, `inspectBuild`, `cutover`까지 이어 가고, 재구축 빌드면 멈추고 다음 단계(`backfill`, `cutover`, `retire-old`)를 출력합니다. dry run은 `inspect`와, 등록되지 않은 key면 `planCreate`만 읽습니다 |
| `backfill` | `[logicalKey] [--build ID] [--limit N]` | 있음 | 아니요 | `done`이 될 때까지 `runBackfillPage` |
| `cutover` | `[logicalKey] [--build ID]` | 있음. `--execute`가 없으면 dry run | 예, dry run은 제외 | `inspectBuild` 뒤 `cutover`. dry run은 `inspectBuild`에서 멈춥니다 |
| `rollback` | `[logicalKey] [--build ID]` | 있음 | 예 | `rollback` |
| `retire-old` | `[logicalKey] [--target ID]` | 있음 | 예 | 지정한 대상, 또는 읽기 대상이 아니고 은퇴하지 않았으며 해제 시각이 있는 모든 대상에 `retireTarget`. 첫 거부에서 멈춥니다 |
| `suspend` | `[logicalKey]` | 있음 | 아니요 | `suspendCapture` |
| `resume` | `[logicalKey]` | 있음 | 예 | `resumeCaptureForRebuild`. 다음 단계(`backfill`, `cutover`)를 출력합니다 |
| `verify` | `--target ID [--limit N]` | 있음(스캔 진행을 기록) | 예 | `done`이 될 때까지 `runTargetVerificationPage`. 위반이 남으면 `verification-violations`로 끝납니다 |
| `resume-target` | `--target ID` | 있음 | 예 | `resumeTarget` |
| `reconcile` | `--target ID` | 있음 | 예 | `confirmQuiescent: true`로 `reconcileCreate` |
| `remark` | `[logicalKey]`와 `--ids ID`, 또는 `--scan source`나 `--scan ledger`와 `[--after X] [--through X]`. `[--limit N]` | 있음 | 아니요 | `remark`. `--ids`면 한 번, 아니면 스캔에 `next`가 없을 때까지 페이지마다 |
| `retry-quarantined` | `--target ID [--ids ID] [--limit N]` | 있음 | 아니요 | `retryQuarantined`. `--ids`면 한 번, 아니면 한 페이지가 `--limit`보다 적게 풀 때까지 페이지마다 |
| `drain` | `[--max-rounds N]` | 있음 | 예 | 없음. `workerLimits`로 워커를 돌려, drain이 할 일을 찾지 못하거나 워커가 cooldown에 들어가거나 drain이 `--max-rounds`번(기본 100) 돌 때까지 실행합니다. 개발용입니다 |
| `adopt-store` | | 있음 | 아니요 | `confirmCopy: true`로 `adoptCopiedStore`, 그다음 저장소 결속. 다음 단계(`restart-processes`, `resume`, `backfill`, `cutover`)를 출력합니다 |
| `confirm-ownership` | | 있음 | 예 | `confirmSoleOwner: true`로 `confirmStoreOwnership`, 그다음 저장소 결속 |

`--limit`은 페이지 크기이고 기본값은 500입니다. `--build`를 주지 않으면 logical key의 열린 빌드를 쓰고, 열린 빌드가 없으면 `no-open-build`로 거부합니다. 상태를 바꾸는 명령은 감사 문맥을 위한 `--operation-id`, `--actor`, `--reason`도 받습니다. 기본값은 작업마다 새 operation ID(`sonamu-search-<command>-<UUID>`), 운영체제 사용자 이름을 붙인 `cli:` actor, `sonamu search <command>` reason입니다.

**승인.** 상태를 바꾸는 명령은 승인을 받아야 실행됩니다. 터미널에서는 CLI가 실행 전에 묻고, `--confirm`을 주면 묻지 않습니다. 터미널이 아니거나 `--non-interactive`를 주면 `--execute --confirm`이 필요하고, 없으면 아무것도 실행하기 전에 종료 코드 3(`CONFIRMATION_REQUIRED`)으로 끝납니다. `init`과 `cutover`는 예외입니다. `--execute` 없이는 dry run으로 실행되며, dry run은 승인이 필요 없고 아무것도 바꾸지 않습니다. `reconcile`, `adopt-store`, `confirm-ownership`에서는 승인이 그 작업이 요구하는 운영자 확인(`confirmQuiescent`, `confirmCopy`, `confirmSoleOwner`)을 대신하므로, 승인하기 전에 복구 절차의 전제 조건을 확인하세요.

**logical key.** 설정의 정의에 logical key가 하나뿐이면 인자를 생략할 수 있습니다. 여럿이면 인자를 받는 명령은 생략할 때 거부하고(`logical-key-required`, key 목록은 `details.keys`), 정의에 없는 key는 `logical-key-unknown`으로 거부합니다. 둘 다 종료 코드 2입니다.

### 출력과 실패

결과가 하나인 명령은 끝날 때 결과를 출력합니다. 사람이 읽는 형식이거나, `--json`이면 `{"ok":true,"command":"search.inspect","data":…}`입니다. `init`(실행할 때), `backfill`, `retire-old`, `verify`, `remark`, `retry-quarantined`, `drain`은 대신 스트리밍합니다. 단계마다 `{"event":"backfill.page","data":…}` 같은 JSON 한 줄을 일어나는 즉시 쓰며, `--json`과 상관없이 같고, 마지막 결과 줄은 따로 없습니다. 이벤트는 `init.plan`, `init.created`, `init.build`, `init.next`, `backfill.page`, `cutover.check`, `cutover.done`, `retire.none`, `retire.start`, `retire.done`, `verify.page`, `remark.page`, `remark.done`, `retry.page`, `retry.done`, `drain.round`, `drain.<워커 이벤트>`, `drain.stopped`입니다.

`--json`이면 실패는 stdout의 한 줄 `{"ok":false,"command":…,"error":{"code","message","hint","details"},"exitCode":…}`입니다. `--json`이 없으면 메시지와 hint를 stderr에 씁니다. `code`는 패키지의 오류 코드(예: `SEARCH_ADMIN_PRECONDITION_FAILED`), `details.reason`은 이 페이지에 나오는 거부 이유, `details.retryable`은 다시 실행해서 성공할 수 있는지입니다. 자격 증명처럼 보이는 `details` 키는 빠집니다. `SearchStoreMismatch`에는 복사본이나 복원본이면 `sonamu search adopt-store`, 같은 저장소면 `sonamu search confirm-ownership`을 실행하라는 hint가 붙습니다. 두 절차는 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)에 있습니다. 스트리밍 명령이 도중에 실패하면 이미 출력된 단계는 반영된 상태이고, 다시 실행하면 멈춘 곳에서 이어 갑니다.

| 종료 코드 | 뜻 |
| --- | --- |
| `0` | 완료 |
| `1` | 작업이 거부되거나 실패함 |
| `2` | 사용법 오류: 알 수 없는 명령이나 옵션, 잘못된 값(`invalid-cli-input`), `logical-key-required`, `logical-key-unknown`, `--ids`나 `--scan` 없는 `remark`(`remark-scope-required`) |
| `3` | `CONFIRMATION_REQUIRED`: 승인 없는 상태 변경 |
| `130` | 운영자가 확인 질문에서 거절함 |


## 첫 대상 만들기

첫 대상과 정의 변경 뒤의 재구축은 같은 흐름입니다. 빌드를 열고, 원본에서 채우고, 워커가 대기를 비우게 한 뒤 cutover합니다.

<Warning>
이 키를 표시하는 코드는 첫 대상을 등록한 뒤에 배포하세요. 그 전에는 표시가 실패해 도메인 트랜잭션이 커밋되지 않습니다([트랜잭션 색인](/ko/advanced-features/opensearch/transactional-indexing)).
</Warning>

```typescript title="search/administration.ts"
export async function backfill(admin: SearchAdmin, build: BuildHandle): Promise<void> {
  for (;;) {
    const progress = await admin.runBackfillPage(build.buildId, { limit: 1_000 });
    if (progress.done) return;
  }
}

export async function buildAndCutover(
  admin: SearchAdmin,
  audit: AdminContext,
): Promise<BuildHandle> {
  const build = await admin.beginRebuild(
    { logicalKey: chatMessagesSearch.key, fingerprint: chatMessagesSearch.fingerprint },
    audit,
  );
  await backfill(admin, build);
  const inspection = await admin.inspectBuild(build.buildId);
  if (!inspection.eligibleForCutover) {
    throw new Error(`cutover 차단: ${inspection.blockers.join(", ")}`);
  }
  await admin.cutover(build.buildId, audit);
  return build;
}
```

시작하기 전에 패키지 스키마가 설치돼 있고, 관리 핸들이 그 정의를 가지고 있어야 합니다.

1. `beginRebuild({ logicalKey, fingerprint }, audit)`로 빌드를 엽니다. 읽기 대상이 없으면 대상을 만들고 첫 빌드(`initial`)를, 있으면 재구축(`rebuild`)을 엽니다. 같은 fingerprint의 열린 빌드가 있으면 아무것도 쓰지 않고 그 빌드를 돌려주므로, 중간에 멈춘 흐름은 같은 호출로 이어 갑니다.

   확인: `inspect().openBuild`에 빌드가 보입니다. `remote-create-ambiguous`로 거부되면 생성 결과를 모르는 것입니다. [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)의 "결과를 모르는 생성"을 따르세요.

2. `runBackfillPage(buildId, { limit })`를 `done`이 돌아올 때까지 부릅니다.

   확인: `inspectBuild(buildId).phase`가 `catching_up`입니다. 호출이 실패하면 다시 부릅니다. 기록된 페이지 커서에서 이어 갑니다.

3. 워커가 새 대상의 대기를 비우게 둡니다.

   확인: `inspectBuild(buildId).eligibleForCutover`가 `true`입니다. 아니면 `blockers`에 이유가 있습니다. "재구축과 cutover"의 표를 보세요.

4. `cutover(buildId, audit)`를 실행합니다.

   확인: `inspect().readHead.targetId`가 새 대상입니다. 거부되면 아무것도 바뀌지 않았으므로, `details.blockers`의 원인을 고치고 다시 실행합니다.

첫 빌드는 되돌릴 대상이 없으므로 cutover와 함께 닫힙니다.

대상 생성만 따로 실행하며 단계마다 살펴보려면, `beginRebuild`가 안에서 실행하는 낮은 수준의 두 작업을 씁니다.

```typescript title="search/administration.ts"
/** Review the plan before executing it; an ambiguous create blocks its target id until reconcileCreate. */
export async function createFirstTarget(
  admin: SearchAdmin,
  audit: AdminContext,
): Promise<TargetHandle | { ambiguous: CreatePlan }> {
  // Required when the handle holds two definitions for the key, as during a rebuild.
  const plan = await admin.planCreate(chatMessagesSearch.key, {
    fingerprint: chatMessagesSearch.fingerprint,
  });
  if (plan.missingPlugins.length > 0 || plan.warnings.length > 0) {
    throw new Error(
      `생성 계획을 확인하세요: ${[...plan.missingPlugins, ...plan.warnings].join(", ")}`,
    );
  }
  try {
    return await admin.executeCreate(plan, audit);
  } catch (error) {
    if (error instanceof SearchAdminPreconditionFailed) {
      if (ambiguousCreateSchema.safeParse(error.details).success) return { ambiguous: plan };
    }
    throw error;
  }
}
```

1. `planCreate(logicalKey, { fingerprint })`를 실행합니다. 아무것도 만들거나 기록하지 않고 계획을 돌려줍니다. 계획에는 새 대상 ID, 물리 인덱스와 쓰기 alias 이름, 보낼 설정과 매핑, `missingPlugins`, 경고(`capture-suspended`, `index-has-live-target`, `plugins-missing`)가 들어 있습니다. 재구축 중처럼 핸들에 같은 key의 정의가 둘 이상이면 `fingerprint`로 하나를 고르고, 하나뿐이면 생략할 수 있습니다.

   확인: `missingPlugins`와 `warnings`가 비어 있습니다. 아니면 멈추고 먼저 해결합니다. 예제는 아무것도 만들기 전에 예외를 던집니다.

2. `executeCreate(plan, audit)`를 실행합니다. 빠진 플러그인이 있으면 아무것도 하지 않고 `plugins-missing`으로 거부합니다. 그렇지 않으면 대상 의도와 생성 시도를 기록하고, 인덱스와 쓰기 alias를 한 요청으로 만들고(인덱스 `_meta`에 저장소 식별자가 들어갑니다), 매핑과 alias를 다시 읽어 확인한 다음, 대상을 등록하고 첫 빌드를 엽니다.

   확인: 대상 핸들이 돌아옵니다. 같은 계획으로 다시 부르면 등록된 대상의 원격 상태만 확인하고 같은 핸들을 돌려주며, 다시 만들지 않습니다. 응답을 잃거나 5xx를 받아 `remote-create-ambiguous`로 거부되면 그 대상 ID는 `reconcileCreate` 전까지 막힙니다. 아래 "원격 생성 상태"를 보세요.

## 재구축과 cutover

정의를 바꾼 뒤 재구축하려면 관리 핸들에 옛 정의와 새 정의를 모두 주고 "첫 대상 만들기"의 단계를 따릅니다. 이때 `beginRebuild`는 `rebuild` 빌드를 엽니다. 빌드는 `created` → `backfilling` → `catching_up` → `serving` 단계를 거칩니다.

- **backfill**: `runBackfillPage(buildId, { limit })`의 첫 호출은 정의의 `captureScanBoundary`로 스캔 상한을 기록합니다. 이후 호출은 `scanSourceIds` 한 페이지를 읽어, 원장에 없는 ID는 리비전 1로 만들고, 새 대상에 지금의 원장 리비전으로 의도를 예약합니다. 마지막 페이지에서 빌드가 `catching_up`이 됩니다. 호출마다 임대를 얻고 반납하며, 페이지 커서를 비교한 뒤에만 쓰므로 같은 페이지가 두 번 반영되지 않고 어느 지점에서 멈춰도 이어서 실행할 수 있습니다.
- **이중 쓰기**: 새 대상이 등록된 순간부터 `markChanged`는 옛 대상과 새 대상 모두에 의도를 기록합니다. backfill 도중의 쓰기와 스캔 상한 뒤에 생긴 ID도 새 대상에 도착합니다.
- **따라잡기**: 워커가 새 대상의 대기를 비웁니다. `inspectBuild(buildId)`가 진행 상황과 cutover 차단 코드를 잠금 없이 보여 줍니다.

| 차단 코드 | 뜻 |
| --- | --- |
| `capture-suspended` | 캡처가 중단됨 |
| `phase-not-catching-up` | 빌드가 아직 따라잡기 단계가 아님 |
| `scan-incomplete` | backfill이 끝나지 않음 |
| `capture-epoch-mismatch` | 빌드가 지금의 epoch에 속하지 않음 |
| `new-target-not-writable` | 새 대상이 쓰기 가능한 활성 대상이 아님 |
| `read-head-moved` | 빌드를 연 뒤 읽기 포인터가 다른 곳으로 옮겨짐 |
| `quarantined-documents` | 새 대상에 격리된 문서가 있음 |
| `pending-above-limit` | 대기가 `maxPendingDocuments`보다 많음 |

대기와 격리 확인은 판정에 필요한 만큼만 셉니다. 대기는 `maxPendingDocuments` + 1행에서 세기를 멈추고, 격리는 있는지만 봅니다. 그래서 대기가 커져도 확인 비용은 늘지 않습니다.

`cutover(buildId, audit)`는 다음을 차례로 확인합니다. 하나라도 걸리면 아무것도 바꾸지 않고 `SearchAdminPreconditionFailed`로 거부합니다(`details.reason`은 첫 차단 코드, `details.blockers`는 전체 목록).

1. 원격 확인: 새 대상의 인덱스가 있고, `_meta`가 이 대상과 이 저장소를 가리키고, 쓰기 alias가 그 인덱스를 가리킵니다. 없는 것을 다시 만들지는 않습니다. 이어서 새 대상의 fence를 확인합니다.
2. 표본 검증: 원장에서 `sampleSize`개 ID를 골라 한 스냅샷에서 projection하고, 새 인덱스의 문서와 리비전, 삭제 여부, 해시를 비교합니다. 새 대상에 아직 대기 중인 문서는 통과합니다. 위반이 있으면 `verification-failed`입니다.
3. 위 표의 차단 코드를 한 트랜잭션 안에서 다시 확인하고, 같은 트랜잭션에서 읽기 포인터와 빌드 단계를 바꿉니다.

`eligibleForCutover`는 PostgreSQL에서 확인할 수 있는 조건만 반영하므로, 1과 2의 결과는 cutover를 실행해야 알 수 있습니다. 재구축 빌드는 cutover 뒤에도 `serving`으로 남아, 옛 대상을 은퇴시키기 전까지 rollback할 수 있습니다.

### rollback

```typescript title="search/administration.ts"
export async function rollbackBuild(admin: SearchAdmin, build: BuildHandle, audit: AdminContext) {
  return admin.rollback(build.buildId, audit);
}
```

`rollback(buildId, audit)`은 `serving` 빌드의 읽기 포인터를 옛 대상으로 돌립니다. 옛 대상이 아직 쓰기 가능하고 같은 epoch이어야 하고, 그 정의가 관리 핸들에 있어야 하며, cutover 뒤 읽기 포인터가 다른 곳으로 옮겨지지 않았어야 합니다. 하나라도 어긋나면 거부합니다. 실행한 뒤 `inspect().readHead.targetId`가 옛 대상인지 확인하세요. 이중 쓰기가 계속되므로 다시 `cutover`할 수 있고, cutover → rollback → cutover를 반복해도 됩니다. 옛 대상을 은퇴시키면 rollback 기회가 끝납니다.

## 읽기 포인터

읽기 포인터는 `read_heads` 테이블의 logical key당 한 행입니다. 지금 읽을 대상, 세대 번호, 재구축이 필요한지 여부, 읽기 수명 최대치를 담습니다. 새 검색은 매번 이 행을 읽고, 커서는 발급 때의 대상에 고정됩니다. cutover가 커밋되기 전에 시작한 검색은 옛 대상에서 끝나고, 커밋 뒤에 시작한 검색은 새 대상을 읽습니다. 포인터가 PostgreSQL에 있으므로 cutover와 rollback은 트랜잭션 하나로 일어나고, OpenSearch alias는 바뀌지 않습니다.

## 읽기 수명

읽기 수명 최대치(`maxSearchLifetimeMs`, `maxCursorLifetimeMs`, `maxPitKeepAliveMs`)와 은퇴 안전 여유는 첫 대상을 만들 때 `read_heads`에 기록됩니다. 그 뒤에 관리 핸들에 준 `lifetimes`는 쓰이지 않습니다. 기록된 값은 `inspect().lifetimes`로 읽고, 네 값을 모두 받는 `changeReadLifetimes(logicalKey, lifetimes, audit)`로만 바꿉니다.

```typescript title="search/administration.ts"
/** Raise the recorded maximum before giving query handles a longer cursor lifetime; lowering it is refused. */
export async function raiseCursorLifetime(
  admin: SearchAdmin,
  maxCursorLifetimeMs: number,
  audit: AdminContext,
): Promise<ReadLifetimeChange> {
  const recorded = (await admin.inspect(chatMessagesSearch.key)).lifetimes;
  if (recorded === null) throw new Error("이 key에는 아직 대상이 없습니다.");
  const next: ReadLifetimes = { ...recorded, maxCursorLifetimeMs };
  return admin.changeReadLifetimes(chatMessagesSearch.key, next, audit);
}
```

- 어느 값이든 올리기와 `maxPitKeepAliveMs` 낮추기는 바로 적용됩니다. 검색 핸들에 더 긴 수명을 주기 전에 기록된 값을 먼저 올리세요. 검색 핸들의 수명이 기록된 값을 넘으면 검색이 `lifetime-exceeds-catalog`로 실패합니다.
- 검색 수명, 커서 수명, 안전 여유를 낮추면 `SearchAdminPreconditionFailed`(`read-lifetime-decrease-unsupported`)로 거부하고 아무것도 바꾸지 않습니다. 은퇴 유예가 이 값들의 합인데, 더 긴 값으로 발급된 커서가 아직 살아 있을 수 있기 때문입니다.
- 실제 커서 수명을 줄이려면 검색 핸들의 설정을 낮추세요. 기록된 값보다 낮은 설정은 언제나 허용됩니다. 기록된 값이 높아서 드는 비용은 은퇴가 기다리는 시간뿐입니다.

감사 기록에는 이전 값과 새 값이 남습니다. 값이 같으면 아무것도 쓰지 않습니다.

## 은퇴

`retireTarget(targetId, audit)`은 더 이상 아무도 읽지 않는 대상을 지웁니다. 물리 인덱스 삭제는 되돌릴 수 없습니다. 은퇴한 뒤에는 그 빌드를 rollback할 수 없고, 그 대상의 이름은 다시 만들어지지 않습니다. 은퇴는 읽기 유예가 지나야 시작합니다.

> 유예 = `maxCursorLifetimeMs` + `maxSearchLifetimeMs` + `retirementSafetyMarginMs`

세 값은 `read_heads`에 기록된 값입니다. 유예는 확정 해제 시각부터 세며, 이 시각은 cutover나 rollback이 커밋된 **뒤에** 기록됩니다. 확정 시각이 아직 없으면 은퇴가 먼저 그 시각을 기록하고 거부합니다. 한 번도 읽기 대상이었던 적이 없는 대상에는 유예가 없습니다. 권장값이면 10분 + 30초 + 5분 = 15분 30초입니다.

```typescript title="search/administration.ts"
/** Returns null once retired, or the earliest retry time in epoch milliseconds while the read grace period lasts. */
export async function retireWhenAllowed(
  admin: SearchAdmin,
  targetId: string,
  audit: AdminContext,
): Promise<number | null> {
  try {
    await admin.retireTarget(targetId, audit);
    return null;
  } catch (error) {
    if (error instanceof SearchAdminPreconditionFailed) {
      const pending = gracePendingSchema.safeParse(error.details);
      if (pending.success) return pending.data.earliestAtMs;
    }
    throw error;
  }
}
```

1. `retireTarget(targetId, audit)`을 실행합니다.

   확인: 호출이 돌아오고 `inspect()`에서 대상이 `retired`입니다. `retirement-grace-pending`으로 거부되면 `details.earliestAtMs`에 다시 실행합니다(예제는 그 시각을 돌려줍니다). 다른 거부는 아래 표를 보세요. 중간에 실패하면 같은 호출이 멈춘 곳에서 이어 갑니다.

은퇴가 하는 일은 순서대로 다음과 같습니다.

1. 확정 해제 시각, 대상의 fence, 거부 조건을 확인하고, 이 대상이 옛 대상인 `serving` 빌드를 닫고, 대상의 쓰기를 끕니다.
2. 인덱스의 `_meta`가 이 대상과 이 저장소를 가리키는지 확인합니다.
3. 쓰기 alias를 지웁니다. 이후 늦게 도착한 bulk는 `require_alias`로 거부되어 인덱스를 만들지 못합니다.
4. alias를 지운 뒤 `leaseDurationMs + requestTimeoutMs`(`workerBounds`)가 지나고 살아 있는 임대가 없을 때까지 기다립니다. 권장값이면 2분 30초입니다.
5. `_meta`와 fence를 다시 확인한 뒤 물리 인덱스를 지웁니다. fence 문서는 인덱스와 함께 사라집니다.
6. 남은 의도와 런타임 행을 묶음으로 지우고 대상을 `retired`로 바꾸며, 같은 트랜잭션에서 fence 행을 지웁니다. 정리가 길어지면 묶음 사이에 관리 임대를 연장합니다.

alias나 인덱스가 이미 없으면 엔진의 404를 성공으로 보고 진행합니다. 스키마 버전 2 이전에 만들어 `_meta`에 저장소 식별자가 없는 인덱스는 대상만 확인합니다.

| 거부 | 뜻 | `retryable` |
| --- | --- | --- |
| `target-serving` | 지금 읽기 대상임 | false |
| `retirement-grace-pending` | 유예가 남음. `details.earliestAtMs`가 가장 이른 시각 | true |
| `remote-create-unresolved` | 생성 시도의 결과를 아직 모름 | false |
| `target-in-open-build` | 열린 빌드의 새 대상임 | false |
| `target-not-retirable` | 은퇴할 수 없는 상태 | false |
| `target-detached` | 복사본 채택으로 떼어 낸 대상. 원본의 것이므로 원본에서 관리합니다 | false |
| `retirement-in-flight` | 기다리는 동안 상한이 지나도 임대가 남음 | true |
| `retirement-residue` | 마지막 정리에서 의도나 런타임 행이 남음 | true |
| `remote-index-foreign` | 인덱스의 `_meta`가 이 대상과 다름. 지우지 않습니다 | false |

인덱스 `_meta`의 저장소 식별자가 이 저장소와 다르면 `SearchStoreMismatch`(`remote-store-mismatch`)로 거부하고 alias와 인덱스를 건드리지 않습니다.

## 캡처 중단과 재구축 재개

캡처 중단은 검색 가용성을 내주고 재구축을 얻는 결정입니다. 원본 데이터베이스를 복원했을 때처럼 원장을 믿을 수 없을 때 씁니다. 절차와 예제는 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)의 "원본 데이터베이스 복원"에 있습니다.

`suspendCapture(logicalKey, audit)`의 결과는 다음과 같습니다.

- `markChanged`가 `"suspended"`를 돌려주고 의도를 남기지 않습니다. 도메인 쓰기는 계속 커밋됩니다.
- 읽기 포인터가 재구축 필요 상태가 되어 검색이 `SearchRebuildRequired`를 받습니다.
- 기존 대상과 열린 빌드가 모두 옛 epoch가 되어 다시는 쓰이지 않습니다. 워커가 가져가지 않고, cutover나 rollback할 수 없고, 그 전에 발급한 커서는 영원히 무효입니다.
- 이미 중단돼 있으면 아무것도 바꾸지 않습니다.

`resumeCaptureForRebuild(logicalKey, audit)`는 새 epoch의 새 대상을 만들고, 그 대상을 등록하는 커밋에서 캡처를 다시 켭니다. 캡처가 중단돼 있지 않으면 원격 명령 없이 거부합니다(`capture-not-suspended`). 돌려준 빌드를 backfill하고 cutover해야 검색이 돌아오며, 이 빌드는 rollback할 수 없습니다.

비용은 이렇습니다. 중단부터 재개 빌드의 cutover까지 검색을 쓸 수 없고, 원본 전체를 다시 채워야 합니다. 중단 동안의 변경은 의도로 남지 않지만, backfill이 원본의 현재 상태를 읽으므로 새 대상에는 반영됩니다. 옛 epoch의 대상은 나중에 은퇴시킵니다.

## 원격 생성 상태

인덱스 생성 요청은 결과를 모르는 채 끝날 수 있습니다. 패키지는 그 결과를 대상마다 상태로 기록하고, 무엇도 스스로 다시 만들거나 지우지 않습니다. 결과를 모를 때의 절차는 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)의 "결과를 모르는 생성"에 있습니다.

| 상태 | 뜻 |
| --- | --- |
| `not_started` | 원격 명령을 보내지 않았거나, 엔진이 명확히 거절해(예: 429) 같은 계획으로 다시 시도할 수 있음 |
| `in_flight` | 시도를 기록했지만 결과를 기록하지 못함(생성자가 멈춤) |
| `verified` | 인덱스와 쓰기 alias, `_meta`를 확인함 |
| `ambiguous` | 요청의 결과를 모름(제한 시간, 연결 끊김, 5xx, 해석할 수 없는 응답) |
| `abandoned` | 엔진이 생성을 거부했거나 조정에서 버린 식별자. 다시 시도하지 않음 |

- `in_flight`나 `ambiguous`인 식별자는 등록, 재생성, 은퇴, 같은 logical key의 다음 생성이 모두 원격 명령 없이 거부됩니다(`remote-create-ambiguous`, `remote-create-unresolved`).
- 이 상태를 풀 수 있는 것은 `reconcileCreate(targetId, { confirmQuiescent: true }, audit)`뿐입니다. 그 식별자를 만들던 프로세스와 요청이 더는 도착할 수 없다는 것을 확인한 뒤에만 부르세요. `confirmQuiescent`는 그 확인을 했다는 표시입니다. 없으면 `quiescence-not-confirmed`로 거부합니다.
- 조정은 원격을 읽기만 하고 아무것도 만들거나 지우지 않습니다. 인덱스, 쓰기 alias, 일치하는 `_meta`가 모두 있으면 `verified`, 아니면 `abandoned`입니다. `abandoned`는 PostgreSQL만 바꾸며 원격 인덱스를 채택하지도 지우지도 않습니다. 남은 인덱스를 지울지는 운영자가 정합니다.
- `verified`면 같은 계획의 `executeCreate`가 원격 명령 없이 등록을 마칩니다. `abandoned`면 그 식별자는 다시 쓸 수 없으므로 새 계획으로 처음부터 만듭니다.
- 같은 이름의 인덱스가 `_meta`가 다른 채로 이미 있으면 `remote-index-conflict`로 거부하고, 채택하지도 지우지도 않습니다. 등록된 대상의 인덱스나 alias가 사라졌으면 `SearchTargetUnavailable`이고 다시 만들지 않습니다.
- 임대나 시도 토큰을 잃은 생성자는 늦게 성공해도 기록하지 못하고, 보상 삭제도 하지 않습니다.

## 상태 점검

`inspect(logicalKey, options)`는 잠금과 임대 없이 한 logical key의 PostgreSQL 상태를 읽습니다. 원격 인덱스는 확인하지 않습니다(대상의 `remote`는 항상 `null`).

| 필드 | 내용 |
| --- | --- |
| `registered` | 이 key가 등록됐는가. 대상 의도가 기록된 적이 없는 key는 오류 대신 `false`이고, 그때는 `binding`과 `workers`만 의미가 있습니다 |
| `captureMode`, `captureEpoch`, `generation` | 캡처 상태 |
| `readHead` | 읽기 대상, 세대, `rebuildRequired` |
| `lifetimes` | 기록된 읽기 수명 최대치와 안전 여유. 읽기 포인터가 없으면 `null` |
| `targets` | 대상마다 상태, 쓰기 여부, 원격 생성 상태, 일시 정지 이유, 해제 시각, 검증 스캔 진행, `backlog`, `fence` |
| `openBuild` | 열린 빌드(`inspectBuild`와 같은 내용) |
| `workers` | 이 key를 처리한다고 알린 워커(워커 ID, fingerprint, heartbeat 나이) |
| `binding` | 저장소 결속: `storeId`, `originRecorded`, `originMatches`, `instanceMatches`. 하나라도 `false`면 워커와 원격 관리 작업이 멈춥니다. key와 상관없이 저장소 전체의 값입니다 |

대상의 `backlog`는 `pending`(격리되지 않은 의도), `quarantined`, `leased`(살아 있는 임대), `delayed`(재시도 대기), `intents`, `oldestPendingAgeMs`와, 수가 정확한지를 나타내는 `exact`와 `limit`을 담습니다. 기본은 bounded 모드라서 수치마다 많아야 10,000행을 읽으므로, 자주 읽어도 대기 크기에 비례하는 일을 하지 않습니다. `exact`가 `false`면 그 수는 "적어도 그만큼"입니다. 상한은 `{ countLimit }`으로 바꿉니다(1~1,000,000). 은퇴했거나 실패했거나 떼어 낸 대상의 `backlog`는 `null`입니다.

```typescript title="search/administration.ts"
/** Safe to poll: each count reads at most countLimit rows, and a count with exact false is a lower bound. */
export async function backlogByTarget(admin: SearchAdmin): Promise<Map<string, TargetLag>> {
  const inspection = await admin.inspect(chatMessagesSearch.key, { countLimit: 10_000 });
  const report = new Map<string, TargetLag>();
  for (const target of inspection.targets) {
    if (target.backlog !== null) report.set(target.targetId, target.backlog);
  }
  return report;
}
```

정확한 수는 대기 크기에 비례하는 시간이 듭니다. 하루 한 번의 보고처럼 드물게만 읽고, 모니터링 주기로는 부르지 마세요.

```typescript title="search/administration.ts"
/** Costs time proportional to the backlog: never call it on a monitoring interval. */
export async function exactBacklogByTarget(
  admin: Pick<SearchAdmin, "inspect">,
): Promise<Map<string, TargetLag>> {
  const inspection = await admin.inspect(chatMessagesSearch.key, { counts: "exact" });
  const report = new Map<string, TargetLag>();
  for (const target of inspection.targets) {
    if (target.backlog !== null) report.set(target.targetId, target.backlog);
  }
  return report;
}
```

대상의 `fence`는 이 데이터베이스가 기록한 fence입니다. `inspect`는 PostgreSQL에서만 읽고 원격 fence는 읽지 않습니다.

| 필드 | 내용 |
| --- | --- |
| `epoch` | 이 데이터베이스가 가진 epoch. fence 행이 없는 대상(첫 전송 전이거나 스키마 버전 1에서 만든 인덱스)은 0 |
| `pending` | 원격에 쓰는 중이거나 결과를 모르는 전진(또는 인수)이 있음 |
| `renewedAgeMs` | 마지막 갱신 뒤 지난 시간(데이터베이스 시계). 갱신한 적이 없으면 `null` |
| `lost` | 이 데이터베이스가 fence를 잃었음. 그 대상에 아무것도 보내지 않습니다 |
| `lostDetail` | `{ class, localEpoch, remoteEpoch }` 또는 `null` |

워커의 `target-fence-lost` 이벤트와 `status().fenceLostTargets`도 같은 상실을 알립니다. `binding`의 값이 모두 `true`인데 fence를 잃었다면, 이 데이터베이스와 바이트까지 같은 다른 데이터베이스(`pg_basebackup`으로 만든 것 같은 물리 복사본)가 같은 OpenSearch 인덱스에 쓰고 있거나 인덱스가 뒤로 간 것입니다. 절차는 [복구 절차](/ko/advanced-features/opensearch/recovery-runbooks)의 "fence를 잃은 대상"에 있습니다.

```typescript title="search/administration.ts"
export async function lostFences(
  admin: SearchAdmin,
): Promise<
  readonly { targetId: string; class: string; localEpoch: number; remoteEpoch: number }[]
> {
  const inspection = await admin.inspect(chatMessagesSearch.key);
  return inspection.targets.flatMap((target) =>
    target.fence.lost
      ? [
          {
            targetId: target.targetId,
            class: target.fence.lostDetail?.class ?? "foreign",
            localEpoch: target.fence.lostDetail?.localEpoch ?? 0,
            remoteEpoch: target.fence.lostDetail?.remoteEpoch ?? 0,
          },
        ]
      : [],
  );
}
```
